ColorMesh: three (later more) boards share colours over Bluetooth LE. No Wi-Fi: forge_net is linked (forge_lvgl's

## Bluetooth design (summary of RESEARCH-BLE.md)

- **Transport: NimBLE, a connectionless advertising flood for state** (every board advertises its own state and
  scans continuously; nothing to provision, no phone) plus **one GATT connection on demand** for the dev-mode
  firmware pull. Not SIG mesh (8-byte vendor payload, ~90 ms per message, needs a provisioner, fights a GATT server),
  not ESP-NOW (Wi-Fi).
- **Advertising**: one legacy advertisement, one manufacturer-data AD, no Flags AD; non-connectable in normal mode
  (nobody can connect); connectable in dev mode wanting firmware, with the dev bit and a `target` byte naming the
  peer. Interval fixed at **20 ms** for three boards (the NimBLE floor; from about six boards: 20 ms for 300 ms
  after a change, then 100 ms). Data changes apply live with `ble_gap_adv_set_data` on a prebuilt 31-byte buffer;
  `seq` bumps only on a state change. Fallback if the controller refuses 20 ms non-connectable:
  `CONFIG_BT_NIMBLE_HIGH_DUTY_ADV_ITVL=y`, or connectable adverts with a Flags AD and connection rejection.
- **Payload** (30-byte AD structure): length, type `0xFF`, company id (2), protocol id, origin id (low byte of the
  address), seq (wrap-aware), TTL (0 = never relay), flags (bit0 holding, bit1 dev mode, bit2 image valid and
  servable, bit3 pending verify), R G B, firmware major/minor/patch, version kind (`-anything.N` → N, `-rc.N` →
  100+N, release → 200, post-release build → 201+N, the order of forge_core's `version.h`), target origin (`0xFF`
  unless dev mode), 14 reserved bytes (effects or relayed entries). On receive: `ble_hs_adv_find_field(MFG_DATA)`,
  check length, company id and protocol byte, copy out inside the callback.
- **Identity**: the public address (`ble_hs_util_ensure_addr(0)`, `ble_hs_id_infer_auto`), the peer table's key,
  shown on the system page and in `cfg`.
- **Scanning**: `ble_gap_disc` forever, passive, 100 ms window = interval, `filter_duplicates = 0`; the callback
  copies a 16-byte record into a FreeRTOS queue (microseconds). The scan is cancelled around `ble_gap_connect()` and
  restarted after `BLE_GAP_EVENT_CONNECT` (`CONFIG_BT_NIMBLE_HOST_ALLOW_CONNECT_WITH_SCAN` stays off, esp-idf
  issue 15258).
- **Peer table** (`mesh_proto.c`, 16 entries by address): RGB, holding, dev mode, version, seq, rssi, last heard
  tick; the own state is one more entry, mixed like a peer's. Release is explicit (every event after the finger
  lifts says `holding = 0`), so peers clear within one interval + 10 ms. Expiry only for a dead or out-of-range
  peer: 3 × steady interval + 100 ms (250 ms at 20 ms); a peer not heard for 10 s leaves the table. A 100 ms fade on
  add and remove hides jitter.
- **Mixing**: sum the holders' colours in linear light, then scale so the largest channel is full (keeps hue and
  brightness; averaging looks dim, clamping drifts to white). A board never receives its own advertisements, so self
  is added locally while its finger is down.
- **Timing targets**: remote light within 85 ms median, 150 ms worst. Three boards at 20 ms: the first report after
  a change arrives within one interval plus 0-10 ms; ten boards: ~24 % per-event loss, still every peer within
  ~150 ms.
- **Firmware pull** (`mesh_fw.c`): every advertisement carries the version and a servable bit (only while the running
  image is `ESP_OTA_IMG_VALID`). A dev-mode board seeing a strictly newer servable version (4-byte pre-filter, then
  forge_core `cmp_ver` on the full strings once connected) picks that peer (highest version, then lowest address),
  advertises connectable with `target` = that peer, and waits. Only the named peer reacts: it connects as central
  (7.5 ms interval, supervision 6 s), then data length 251, MTU 512, `ble_gattc_exchange_mtu`, connection update, 2M
  PHY, and streams the image with Write Without Response (~500 kbps at 1M, up to ~1.3 Mbps at 2M: 2 MB in 12-34 s).
  GATT service (custom 128-bit UUID) on the dev board: `CTRL` (START with length and SHA-256, ABORT), `DATA`
  (509-byte writes: sector index, packet seq, 506 bytes; the last packet of each 4 KB sector tagged `0xFF` with the
  sector CRC16), `ACK` (notify, per sector); sender window of 4 sectors; `BLE_HS_ENOMEM` = back off one tick. Sender:
  `esp_image_get_metadata` for the exact length, read through `esp_partition_mmap`. Receiver: checks the first 288
  bytes (magic, same `project_name`, strictly higher version, not the last invalid partition's) before writing;
  `esp_ota_begin(OTA_WITH_SEQUENTIAL_WRITES)`, `esp_ota_end` (verifies the SHA-256), set boot partition, restart.
  The new image boots `PENDING_VERIFY` and confirms itself after 60 s of normal running, else the bootloader rolls
  back; never restart a board in its first 60 s after an update (espforge L23). One pull at a time; a failed pull
  waits 30 s. `fwpull <addr>` sets the target by hand.

### Radio measurements (the report's risks)

Measured on board A alone, 2026-10-31 (v0.1.0-rc.0 test builds):

- Risk 1: `ble_gap_adv_start()` at 0x20 (20 ms), non-connectable, returns 0; `where` shows `ble_adv=32`. No fallback.
- Risk 2: the first build heard neighbours only in bursts (3-4 reports/s, each device once every 2.7 s). Cause:
  `CONFIG_BT_NIMBLE_HOST_QUEUE_CONG_CHECK=y` (the research report's table recommended it) makes the host pass each
  address once per ~200 reports (`ble_hs_hci_evt.c`, `ble_check_adv_list`). With it off: 71-75 reports/s from ~13
  neighbours at a 100/100 ms scan; the strongest steady neighbour (-51 dBm) is heard 17.4 times/s, one report every
  ~57 ms, largest gap 163 ms, no multi-second hole. Three boards (A on the PC, B and C on chargers, same desk): A hears 61 ColorMesh reports/s of the 100/s
  the two peers send (61 % per event at the 100/100 ms scan; 127 reports/s in all with the neighbours). A peer's
  hold or release reaches A's mix within 0-1 ms of the report; the 20 ms advertising makes a missed event cost
  20 ms. Blue + chartreuse gave #80ffff (additive, normalised).
- Risk 3: at ~75 reports/s the report queue never holds more than 1 of 32, the GAP callback takes at most 67 us,
  drops 0 (`where`: `ble_q=1/32 ble_cb=67us ble_drop=0`).
- Risk 7: `heap` after host sync: internal 149 KB free, largest block 78 KB, PSRAM 5552 KB; app .bin 1,091,024 bytes
  (3 MB slot). NimBLE host pools stay in internal RAM (`MEM_ALLOC_MODE_INTERNAL`).
- Hold to mix on the own board: `mesh: hold on` to `mesh: mix` 1-2 ms; release 20 ms.
- Risk 5: the dev-mode pull A <- B (forced `fwpull`, A receiving, display on): 1,124,336 bytes in 51.0 s, 21.4 KB/s,
  0 resent, MTU 512; then `fw: pending verify` and `fw: confirmed` 60 s after the restart, `fwinfo state=valid`.
  Read from the sender (A serving B and C, rc.3-rc.5 test builds): the link had everything the design asks,
  `fw: link dle tx=251 rx=251`, `phy tx=2M rx=2M (update status 0)`, `itvl=7.50 ms latency=0`, `mtu=512`, and still
  22.5 KB/s with 48 of 49 s spent in the mbuf back-off (`48161 ENOMEM`, window wait 0.35 s): the host was never the
  limit, the controller sent one 251-byte packet per 7.5 ms event (509 B per 22.5 ms) while the flood's 100/100 ms
  scan was open. 200 KB probes (`fwtune probe=200`) against the sender's scan window during the transfer:
  100 ms = 22 KB/s, 70 = 32, 50 = 40, 30 = 52, 0 = 75 KB/s; advertising off, window 8, `max_ce_len` 48 and rc.1's
  all-at-once link set-up changed nothing (0 resent everywhere). Fix: the sender scans 30 ms of every 100 ms while
  it serves (`XFER_SCAN_MS`), the receiver pauses its scan while it pulls. Full pulls of the rc.5 image (1,136,224 bytes) read on the sender: to B in 20.9 s (52.9 KB/s, stream 53.4, 0 resent, window wait 156 ms), to C in 22.1 s (50.1 KB/s, 0 resent), with `mesh: peer` lines from the third board arriving during both transfers; C's first attempt lost the link at 676 KB (the peer dropped out, cause not visible from A) and succeeded 30 s later.


## Display pipeline

espforge's forge_lvgl and the board's `display.c`: draw buffers in internal RAM, LVGL's heap in PSRAM, moves between
pages drawn as pictures (slide.c). Nothing here is DMA-read from flash, so `esp_ota_write` during a pull only pauses
the display (`CONFIG_SPI_FLASH_WRITE_CHUNK_SIZE=4096` keeps each pause short).

## Screens (`forge.json` `screens`: `pick main system game voice message`)

- **pick**: 12 swatches on a ring (hue every 30°), centre "Pick your colour / Tap one"; the saved colour is
  pre-highlighted; a tap saves it (NVS) and shows `main`.
- **main**: edge ring 14 px in the own colour; centre = the mix (black when nobody holds, with a dim "hold to send
  your colour" hint); a row of small dots, one per peer in its colour, bright while it holds; a line "N near ·
  vX.Y.Z"; `DEV` badge in dev mode; a progress arc during a firmware pull. **Hold** = finger down on `main`, from
  the board's touch state (not a 400 ms long press: latency); off on release, on PRESS_LOST, or when a drag starts.
  The UI only sets a flag; the mesh task does the radio (espforge L164).
- **system**: second pager page (swipe): version, Bluetooth address, memory, uptime, the peers with versions, dev
  mode.
- **game**: last pager page (swipe left twice from main): rock paper scissors (see "Rock paper scissors" below).
- **voice**: last pager page (right of game): hold to talk, the green Call button (see "Voice clips and calls" below).
- **message**: as espforge's starter (a text, for the console and the harness).

## Settings (NVS)

`config.c`: colour (`#rrggbb`), dev mode (bool), name (up to 16 bytes, UTF-8), brightness (0-100); typed keys, not a
blob (L68); a missing key keeps its default. Changed only from the USB console (`color`, `devmode`, `name`,
`bright`), which the Pages card drives. `cfg` answers everything in one JSON line (PROTOCOL.md §2).

## Languages

English and French (Canada), espforge's i18n: display texts in `main/i18n_strings.h`. The Pages site is English.

## Updates

Partition table: two OTA slots, otadata, NVS, core dump (`partitions.csv`); `CONFIG_BOOTLOADER_APP_ROLLBACK_ENABLE=y`.
Three ways in: the Pages site over USB (esp-web-tools, the parts of a release at their offsets, NVS kept), esptool
with the full image (erases NVS), and the dev-mode pull from a peer (the app part only, verified by `esp_ota_end`,
rolled back by the bootloader if the new image doesn't confirm itself within 60 s). No board polls the site: the
site serves people, not devices. Version order as forge_core: `vX.Y.Z-anything < vX.Y.Z-rc.N < vX.Y.Z < vX.Y.Z-N-gHASH`;
a board pulls only a strictly higher version with the same `project_name` (`colormesh`).

## Known issues / TODO

<!-- One bullet each, with the version it was seen in. -->

- forge_net is linked but never started (v0.1.0-rc.1): forge_lvgl's `screens.h` includes `web.h`; espforge backlog.
- The advertising interval is fixed at 20 ms (v0.1.0-rc.1); the burst-then-100 ms scheme for six boards and more is

### Display: tear-free frames (components/board, 2026-10-31)

The board driver is a local copy of espforge's with: the panel's TE line read on GPIO13 (59 Hz, high 0.63 ms during
the vertical blank), LVGL rendering in DIRECT mode into one 434 KB PSRAM frame, dirty rows pushed as whole 32-row
bands through the two internal DMA buffers right after the TE edge (raw frames for swipes) or, for LVGL frames, as soon
as the scan is too far down to be caught (max wait ~6 ms). Measured: full redraw 31-36 ms render + 15 ms push, every
push ends before the scan (15.9 vs 16.2 ms), 0 TE timeouts, swipes at 54-57 fps. Console `te [lvgl|raw|chase on|off]
[log N]`; `fps` has push and TE fields. Internal RAM unchanged (134 KB free), PSRAM -430 KB. Known risk: an edge
start leads the scan by ~0.6 ms at the top; a long stall of the LVGL task there (NVS write) can still tear one
refresh. To port to espforge's board (backlog).

### Waves (main/wave.c, mesh.c, ui.c; 2026-11-01)

A tap on the main screen (centre within 100 px, else the quadrant) calls `mesh_start_wave(kind)`: the own wave starts
at once; the advert carries `effect` (1-5) and `effect_seq` at payload bytes 17-18 for 1 s. A peer whose
(effect, effect_seq) is new starts that wave at receiver time in the peer's colour (`mesh_waves()`). Bytes 19-21
carry the sender's chosen colour B (0,0,0 = automatic, the opposite hue; v0.3.0): a long press on a ring swatch sets
it (NVS `rgb2`), console `color2`, the USB card's "Wave colour" row. While a wave
is active and the main page is shown, an LVGL timer (33 ms) paints the screen with `display_raw_frame` and
`wave_fill()` (pure C: colour A = the sender's colour, B = `wave_opposite`, pitch 64 px, 160 px/s, 4 s with a
500 ms fade; waves summed per pixel in linear light and normalised, holders' solid colours added; the edge ring
kept). Tables: a 234x234 quarter distance table in PSRAM (86 KB, 0.5 s to build at boot). Measured on board A: one
wave 29 fps, fill 6.2 ms; five waves 21 fps, fill 24 ms avg / 60 max. Console `wave <kind>`, `shot wave` (the raw
frame; `shot main` shows the LVGL page underneath). Peer waves verified on three boards: centre from one, left
from another, both merged.

### Rock paper scissors (main/rps.c, mesh.c, ui.c; v0.5.0)

Flow B of the mockups (the user, 2026-11-01): a tap on the game page starts a round on every board near; 3 s
countdown ("Rock", "Paper", "Scissors!", a white arc on the ring); each player taps a pick before 0 (changeable until
then; a tap on an icon to start also picks it); 600 ms later the picks heard decide, and every board shows the result
for 4 s. Advert bytes 22-25: round seq (0 = none), starter origin, time left to the reveal in 100 ms steps (0 after),
the pick; kept 5 s after the reveal. A board that hears a round id it does not know, with time left, joins it with the
reveal at heard time + left (rps_join); two rounds started at once: the lower starter origin wins on every board.
Outcome: one kind or all three = draw, two kinds = the winning kind wins, no own pick = too late. The game bytes are
not in `mp_table_update`'s "changed" (they move every 100 ms) and the advert is re-encoded (seq bump) at most every
50 ms tick during a countdown. Verified on three boards (rc.1): B started, A joined with 3000 ms left and showed the
result 3.6 s later; picks scissors, rock, paper gave a draw.

### Voice clips and calls (main/clip.c, mesh.c, ui.c; v0.6.0)

The user's choices (2026-11-01): record on a new fifth page, receivers play at once, and true multicast (one send for
every board, not one link per board).

- **Radio layout**: `CONFIG_BT_NIMBLE_EXT_ADV=y`. The flood is extended advertising instance 0 with **legacy PDUs**
  (`legacy_pdu = 1`, same 20 ms, same 30 bytes): on air nothing changed, and boards on older firmware still hear it.
  Scanning stays `ble_gap_disc` (NimBLE runs it as an extended scan; reports come as `BLE_GAP_EVENT_EXT_DISC`, only the
  legacy ones go to the flood queue). `ble_gap_connect` maps to `ble_gap_ext_connect` on its own. Gate measured on
  three boards (rc.1): 58-60 ColorMesh reports/s (62 before), holds mixed as before, firmware pulls 52 KB/s.
- **Send**: hold on the voice page, up to 5 s (16 kHz mono, both microphones averaged, DC removed, a quiet clip scaled
  up to peak 26000, at most x8), then IMA ADPCM 4:1: 5 s = 40,000 bytes. Instance 1 is a non-connectable extended set
  (SID 1, 100 ms, 2M secondary PHY) with a **periodic train every 10 ms**. The clip is cut into 224-byte chunks
  (`clip_chunks.h`: one manufacturer AD, `0x43 'V'`, origin, clip id, chunk, total, length, CRC-32, data; 244 bytes,
  one AUX_SYNC_IND) and the sender changes the periodic data every 10 ms, 3 rounds over all chunks: 5 s of voice
  (179 chunks) takes 5.4 s on air for any number of boards. While the train runs the flood advert carries
  `MP_F_CLIP` (0x20), byte 26 the clip id and byte 27 the length in 100 ms.
- **Receive**: a peer heard with `MP_F_CLIP` and a clip id not yet seen from its address (mesh.c `clip_peer`) goes to
  the clip task, which calls `ble_gap_periodic_adv_sync_create(addr, SID 1, timeout 1 s)`. Each
  `BLE_GAP_EVENT_PERIODIC_REPORT` is parsed and copied in (bitmap, under `rx_lock`, in the host task); the clip plays
  once every chunk is in and the CRC-32 matches. No sync within 4 s, a lost train or a bad CRC drops it
  (`clip: … dropped`). One hop only: a board out of the sender's range gets nothing.
- **Call**: the Call button (or `ring`) sends effect `MP_EFFECT_RING` (6) with a new effect seq for 1 s, like a wave,
  through the flood. Every other board rings and shows "Appel entrant" / "Toucher l'écran pour répondre" in the
  caller's colour, 3 phrases with 3.2 s between them. A tap answers: effect `MP_EFFECT_ANSWER` (7) with byte 28 =
  the caller's origin, for 1 s (`mesh_answer`). The caller shows "Appel en cours…" in its own colour; answers count for the callees' whole ring + 2 s (`calls.c`, host-tested), each board once, and each new one adds a dot in its colour under "Appel répondu" and plays the doo-di-dit (`ringtone_answered`: A5 90 ms, C#6 90 ms, E6 140 ms, the same buzzer synth; the user's pick of ten). The screen stays 4 s after the latest answer; a later answer opens it again; a tap closes it and ends the call (rc.6: B then C answered, two dots, two sounds).
- **Call button**: 170 x 60 with a 40 px touch margin (rc.6: a press 21 px under a 20 px margin missed); a press on the page at or below the margin's top never records (`ui: voice press at x,y (near the button: no recording)`). rc.7: 6 presses, 6 calls.
- **Speaker wake-up**: every sound starts with 250 ms of silence after `esp_codec_dev_open` (rc.3 lost the ring's
  first note, 117 ms, while the amplifier and the DAC woke up).
- **Ring tone** (`ringtone.c`): the timing and timbre measured from a recording of the old phone the user supplied:

### Secure updates: the paired admin board (main/mesh_fw.c, fw_auth.c; v0.4.0)

The user chose a paired admin over signed releases. The admin board (`admin on`) holds an ECDSA P-256 key pair
(NVS `adm_priv` 32 bytes, `adm_own` 64 bytes; plain flash: whoever holds the admin board can push firmware) and
advertises flag bit4 `MP_F_ADMIN`. Other boards store the admin's public key once over USB (`trust <base64>`, NVS
`adm_pub`). A board out of dev mode with a trusted key targets only an admin peer with a newer servable version.
On the link: the admin writes CTRL 04 (challenge request); the receiver notifies a fresh 32-byte nonce (ACK, sector
0xFFFE, status 3, single use, 10 s); the admin answers CTRL 03 = nonce, image length, SHA-256 digest, version (32
bytes) and a deterministic ECDSA signature (r||s) over SHA-256 of those 100 bytes; the receiver checks nonce,
version strictly newer, signature (constant-time compares, keys zeroed after use), notifies a verdict (status 4),
then accepts only a START whose length and digest are the signed ones, requires the image's own version to equal the
signed one, hashes every byte it writes and compares with the signed digest before `esp_ota_end`. Refusals log
`fw: refused <addr>: no proof | bad signature | nonce ... | START does not match the signed image` and back off
30 s. Dev mode: the proof is checked when offered, never required. fw task stack 6 KB; the DRBG and buffers in
PSRAM; +48 KB flash; sign ~110 ms, verify ~215 ms on the board. Host tests: tests/host/test_fw_auth.c (81 checks).
