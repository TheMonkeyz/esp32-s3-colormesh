# BLE on ESP32-S3 / ESP-IDF v5.5.4: RAM, flash, PSRAM eligibility, Kconfig knobs, and Wi-Fi coexistence (three designs)

Scope: ESP32-S3 only, ESP-IDF v5.5.4 as installed at `C:\Espressif\esp-idf` (read directly; file paths + line numbers below are from that tree). Designs: (1) NimBLE legacy advertising + continuous scanning only (broadcaster + observer, no connections/GATT/security); (2) NimBLE with 2-9 GATT connections (central + peripheral); (3) ESP-BLE-MESH on NimBLE or Bluedroid. Baseline device: Wi-Fi STA always connected, HTTPS/mbedTLS, LVGL in 8 MB octal PSRAM, ~100 KB internal RAM free (largest block ~31 KB), ~93 KB DMA-capable free, 1.84 MB app in a 3 MB OTA slot.

Context from the project's own build config (`C:\Users\lmathieu\ESPDEV\esp32-s3-rtcquebec\build\v55\sdkconfig`): `CONFIG_SPIRAM_USE_MALLOC=y` (line 1235), `CONFIG_SPIRAM_MALLOC_ALWAYSINTERNAL=16384` (1237), `CONFIG_SPIRAM_MALLOC_RESERVE_INTERNAL=32768` (1239), `CONFIG_SPIRAM_ALLOW_BSS_SEG_EXTERNAL_MEMORY=y` (1240), `CONFIG_SPIRAM_ALLOW_STACK_EXTERNAL_MEMORY=y` (2893), `CONFIG_ESP_WIFI_IRAM_OPT=y` (1411), `CONFIG_ESP_WIFI_RX_IRAM_OPT=y` (1413), `CONFIG_ESP_WIFI_STA_DISCONNECTED_PM_ENABLE=y` (1425), `CONFIG_ESP_COEX_ENABLED=y` (804), `CONFIG_MBEDTLS_EXTERNAL_MEM_ALLOC=y` (1877), `CONFIG_ESP32S3_INSTRUCTION_CACHE_SIZE=0x4000` (1275), `CONFIG_ESP32S3_DATA_CACHE_SIZE=0x8000` (1285), `CONFIG_COMPILER_OPTIMIZATION_PERF=y` (608), `CONFIG_ESPTOOLPY_FLASHSIZE_16MB=y` (568). ## Key question 1: RAM cost (internal DRAM, PSRAM-eligible RAM) of each design, what can be pushed to PSRAM, and the Kconfig knobs that shrink it

### Takeaway
On the ESP32-S3 the BLE controller (ROM + `libbtdm_app.a`) allocates everything it needs from internal, DMA-capable RAM (`MALLOC_CAP_INTERNAL|MALLOC_CAP_DMA`) and its code needs "over 20 KB" of IRAM; those costs cannot be moved to PSRAM. The NimBLE host's dynamic allocations (its mbuf/HCI pools, roughly 21 KB at defaults, ~11 KB at the "mini" settings) can be moved wholesale to PSRAM with `CONFIG_BT_NIMBLE_MEM_ALLOC_MODE_EXTERNAL`, which is selectable because the project already has `SPIRAM_USE_MALLOC=y`; task stacks (controller 3,584 B, host 4,096 B / 5,120 B with mesh, mesh adv task 3,072 B) stay internal. Espressif publishes no measured per-design totals for the S3; the only numbers in the IDF tree are per-item (828 B per controller activity, 35 B per cached adv report, ~1 KB host DRAM per connection on the newer chips), so the per-design totals below are estimates.

### Cited Findings

**Controller (ESP32-S3 uses the esp32c3-family controller code: `components/bt/controller/esp32c3/`)**

### Inferences
- Computed from the Kconfig defaults and pool macros above (estimate, 4-byte alignment, mbuf overhead ~36 B assumed): NimBLE host pools at defaults ≈ MSYS_1 12×256 = 3,072 B + MSYS_2 24×320 = 7,680 B + EVT 30×72 = 2,160 B + EVT-discard 8×72 = 576 B + ACL 24×~296 ≈ 7,100 B + 1 cmd buffer 259 B ≈ **20.8 KB**; with the `.mini` settings (6/12/12/15) ≈ 1,536 + 3,840 + 1,080 + 576 + 3,552 + 259 ≈ **10.8 KB**. With `BT_NIMBLE_MEM_ALLOC_MODE_EXTERNAL` all of this goes to PSRAM (plus the host's other `nimble_platform_mem_*` allocations: connection objects, GATT procs, L2CAP channels, which Espressif sizes at "about 1k DRAM" per connection on the newer chips). PSRAM-resident HCI buffers are a latency/throughput risk only for high-rate GATT traffic; for design 1 (adv/scan) and low-rate GATT it is the standard remedy on PSRAM boards (the ESP-BLE-MESH FAQ recommends exactly this for Bluedroid: "BT/BLE will first malloc the memory from the PSRAM" — `docs/en/api-guides/esp-ble-mesh/ble-mesh-faq.rst:539-541`).
- What stays internal in every design (estimate of the floor): controller task stack 3,584 B (+`TASK_EXTRA_STACK_SIZE`); NimBLE host task stack 4,096 B (5,120 B with mesh); controller IRAM code "over 20 KB" (Kconfig), which on the S3 is taken from the same SRAM as the heap; coexist code ≈ 9 KB IRAM (with `ESP_WIFI_IRAM_OPT=y`) + 0.8 KB data; controller static data+bss ≈ 1.1 KB; controller heap = 828 B × `BT_CTRL_BLE_MAX_ACT` + 35 B × `ADV_REPORT_FLOW_CTRL_NUM` + duplicate cache (100 entries, size undocumented) + controller environment (undocumented). All of this must come from the DMA-capable internal pool (93 KB free today), and the largest free block of 31 KB is the practical ceiling for any single allocation (the biggest single items are the task stacks, 3.5-5 KB, so fragmentation should not block init).
- **Design 1 (adv + scan, no connections) estimate**: `BT_CTRL_BLE_MAX_ACT=2` (1 adv + 1 scan) → 1,656 B; flow-control cache 3.5 KB (or 0 with `FLOW_CTRL_SUPP=n`, at the cost of silently dropped reports); NimBLE with `ROLE_CENTRAL=n`, `ROLE_PERIPHERAL=n`, `SECURITY_ENABLE=n`, `50_FEATURE_SUPPORT=n` (as in `blecent/sdkconfig.ci.observer` plus broadcaster) and `.mini` pool counts. Rough internal-RAM budget ≈ 20+ KB IRAM (controller) + 9 KB IRAM (coex) + 3.6 KB + 3.2-4.1 KB stacks + ~5-8 KB controller heap items + unknown controller env ⇒ **roughly 45-60 KB of internal SRAM, of which ~11-21 KB of host pools can be in PSRAM** (so ~35-50 KB internal if `MEM_ALLOC_MODE_EXTERNAL`). The S3-specific "45 KB free-heap drop at init" from NimBLE-Arduino#1046 (default Arduino NimBLE config, all internal) is consistent with this. Against the stated 100 KB free / 93 KB DMA-capable, design 1 fits but roughly halves the headroom; the controller's IRAM share is the part that cannot be tuned away except with `BT_CTRL_RUN_IN_FLASH_ONLY` (which has an open stall bug, see Known issues).
- **Design 2 (2-9 GATT connections) estimate**: add 828 B per connection in the controller (`BT_CTRL_BLE_MAX_ACT` must be ≥ connections + 1 adv + 1 scan, max 10 → at most 8 connections while still advertising and scanning, or 9 with no scan), ~1 KB host per connection (Espressif's figure for the newer chips; the S3 host code is the same NimBLE), security code (SMP + TinyCrypt/mbedTLS CMAC) and GATT client/server; Espressif's multi-connection examples raise `MSYS_1_BLOCK_COUNT` to 100 and `GATT_MAX_PROCS` to the connection count (`examples/bluetooth/nimble/ble_multi_conn/ble_multi_conn_cent/sdkconfig.defaults:8-10`), i.e. pool growth, not just per-connection structs. **Rough delta over design 1: +10-15 KB at 2 connections, +25-40 KB at 9 connections**, most of it PSRAM-eligible under EXTERNAL mode except the 828 B/activity controller part and any extra task stacks. Expect ~55-75 KB internal at 9 connections with host pools in PSRAM (estimate).
- **Design 3 (ESP-BLE-MESH) estimate**: see Key question 3; adds a 3,072 B mesh adv task stack (internal), +1 KB host task stack, +8 msys blocks (~2 KB), 60 adv buffers, replay/msg caches, and the GATT server + SMP that mesh needs (PB-GATT/Proxy). Mesh mallocs can go to PSRAM (`BLE_MESH_MEM_ALLOC_MODE_EXTERNAL`) but its FreeRTOS objects/stack cannot on the S3 (the static-alloc option is ESP32-only, see Q3). **Rough: +20-40 KB internal over a GATT-capable NimBLE baseline when mesh mallocs stay internal, +8-15 KB when they go to PSRAM** (estimate; no measured mesh numbers exist for the S3).
- Order of the Kconfig levers by expected effect, all cited above: (1) `BT_NIMBLE_MEM_ALLOC_MODE_EXTERNAL` (moves ~all host heap to PSRAM); (2) pool counts `MSYS_1/2_BLOCK_COUNT`, `TRANSPORT_ACL_FROM_LL_COUNT`, `TRANSPORT_EVT_COUNT` (≈10 KB between default and mini); (3) `BT_CTRL_BLE_MAX_ACT` (828 B each); (4) `BT_CTRL_BLE_ADV_REPORT_FLOW_CTRL_NUM` (35 B each) and `SCAN_DUPL_CACHE_SIZE`; (5) roles/security/5.0/services off (code + static data, unquantified); (6) `BT_NIMBLE_MEMPOOL_RUNTIME_ALLOC` and `BT_NIMBLE_LOW_SPEED_MODE` (new, unquantified); (7) `BT_CTRL_RUN_IN_FLASH_ONLY` (>20 KB IRAM, but see known issue #19297).

### Gaps

## Key question 3: ESP-BLE-MESH specifics (RAM footprint, NVS, Kconfig cuts, NimBLE on S3 in 5.5.4)

### Takeaway
ESP-BLE-MESH is supported on the ESP32-S3 and runs on either host; the mesh examples carry a `sdkconfig.ci.nimble` variant, and `docs` describe the NimBLE adapter. Its footprint is governed by buffer counts (60 adv buffers, replay/msg caches of 10, seg counts) and features (Relay/Proxy/PB-GATT default on; Friend/Low Power/Provisioner default off); `BLE_MESH_MEM_ALLOC_MODE_EXTERNAL` moves its mallocs to PSRAM, but the FreeRTOS-object/stack-in-PSRAM option is ESP32-only. ### Inferences
- Mesh on NimBLE forces a larger NimBLE than design 1: it needs the peripheral role + GATT server (PB-GATT/Proxy service), SMP/crypto (provisioning uses ECDH), `BT_NIMBLE_VS_SUPPORT`, and it raises the host task stack to 5,120 B. So its memory is design-2-like plus the mesh layers; the mesh-only increments are: adv task stack 3,072 B (internal), +8 msys blocks ≈ 2 KB, 60 adv buffers (each a `net_buf` of ~29-31 B payload plus headers; ≈ 4-6 KB, estimate), caches (CRPL 10 + msg cache 10, each entry a few bytes), model/element tables, plus the second controller duplicate-scan cache (100 entries, size undocumented, internal DMA RAM).
- Cheapest mesh configuration for this device: node only (`PROVISIONER=n`, `FRIEND=n`, `LOW_POWER=n`), `PB_GATT=n` and `GATT_PROXY_SERVER=n` if provisioning can be done over PB-ADV and no phone proxy is needed (this removes the GATT server dependency), `RELAY` off if the node must not relay, `ADV_BUF_COUNT` lowered toward the minimum needed for the largest message (ADV_BUF_COUNT ≥ outgoing segments + 3), `TX_SEG_MAX` reduced from 32 to the largest real message, `BLE_MESH_MEM_ALLOC_MODE_EXTERNAL`, `BLE_MESH_NO_LOG=y`, and `BLE_MESH_V11_SUPPORT=n` if 1.1 features are not needed (unquantified saving).
- NVS wear: with the default 0 timeouts every sequence-number increment and RPL change is written to flash; set `SEQ_STORE_RATE` and `RPL_STORE_TIMEOUT` > 0 if the node is chatty. The existing app's NVS partition is shared unless `BLE_MESH_SPECIFIC_PARTITION` adds a `ble_mesh` partition (which would change the partition table of an OTA-deployed device).

### Gaps
- No measured ESP-BLE-MESH RAM or flash figures for any chip were found in the v5.5.4 docs, Kconfig help, or release notes; forum anecdotes (e.g. "DRAM use was about 130 KB with Wi-Fi and mesh", ESP32) could not be verified and are omitted from the findings.
- Per-buffer size of mesh adv buffers and the static `.bss` of the mesh stack were not computed (would require a build).

## Key question 4: Wi-Fi STA / BLE coexistence on the ESP32-S3 (mechanism, support table, power-save, knobs, documented and measured effects)

### Takeaway
The S3 has one 2.4 GHz radio; coexistence is priority-based time-division arbitration run by software (`CONFIG_ESP_COEX_SW_COEXIST_ENABLE`, default y when both stacks are on). The v5.5.4 support table marks every Wi-Fi STA state (scan/connecting/connected) × BLE (scan/advertising/connected) as "Y: supported and the performance is stable"; "S" applies only to ESP-NOW RX, "C1" (unstable) only to SoftAP connecting/connected and sniffer. In the Wi-Fi-connected + BLE-connected scheme Wi-Fi and BLE each get 50 % of a coexistence period that starts at the Wi-Fi TBTT and is >100 ms; BLE scan windows are cut short by Wi-Fi slots (Espressif's FAQ advice: set scan window = scan interval), and in coexist mode Wi-Fi only runs in its slice even with `WIFI_PS_NONE`. Espressif publishes no BLE latency, scan-miss-rate, or Wi-Fi-throughput numbers for coexistence; the only quantitative statements are an old example README ("in theory ... drop to half") and one S3 user report (3 % → 20 %+ BLE packet loss with Wi-Fi/Matter active).

### Cited Findings
**Mechanism and policy (`C:\Espressif\esp-idf\docs\en\api-guides\coexist.rst`)**
- "Each type of board has only one 2.4 GHz ISM band RF module, shared by two or three modules. Consequently, a module cannot receive or transmit data while another module is engaged in data transmission or reception. In such scenarios, ESP32-S3 employs the time-division multiplexing method" — coexist.rst:9.

- Old Espressif example README (`ble_mesh_coex_test`, removed from the v5.5.4 tree): "in theory, the performance of BLE and Wi-Fi coexistence will drop to half of the performance in BLE Only mode or Wi-Fi Only mode" — https://codex.ac6.fr/Zephyr/xref/hal_espressif-3.4.0/examples/bluetooth/esp_ble_mesh/ble_mesh_coex_test/README.md (mirror of an older IDF).
- S3 user measurement (forum, unverified): "If I run the use standalone BLE on the S3 I get a perfectly acceptable 3% packet loss. The problem is when I turn on esp-matter, then the packet loss jumps to 20%+, with some long streaks of 100% loss"; moderator: no ACKs in BLE scanning, so some loss is expected; use a connection if zero loss is needed — [esp32.com p=126440](https://esp32.com/viewtopic.php?p=126440) (search snippet; page itself not readable).
- Third-party summary (no test setup given, do not rely on it): "20-40 % Wi-Fi throughput drop when BLE is active" — https://applied-ee.github.io/embedded/docs/networking/protocol-selection/radio-coexistence/ .
- Wi-Fi throughput reference (no coexistence): the Wi-Fi guide's throughput table is "the best throughput results gained in Espressif's lab and in a shielded box" (e.g. ESP32 TCP RX 20 Mbit/s in air, 65 Mbit/s shield-box) — wifi.rst:2262-2306; no coexistence column exists.

### Inferences
- For this device (STA connected, BLE scan + adv): expected effects from the documented policy are (a) BLE scan effectively duty-cycled to roughly the BLE half of each ≥100 ms period while the STA is connected, so a continuous scan sees roughly half the air time, and a scan window longer than the BLE slice is truncated — hence "window = interval" and expect missed advertisements from devices that advertise rarely; (b) advertising events are delayed when they fall in the Wi-Fi slice except the periodic high-priority event ("1 in N"), so advertising interval jitter up to a Wi-Fi slice (tens of ms) is the normal case; (c) HTTPS/Wi-Fi throughput roughly halves while BLE is active (the "drop to half" theoretical statement), and Wi-Fi is additionally forced to sleep outside its slice even with `WIFI_PS_NONE`. Design 1 (observer + broadcaster) is the least sensitive to this because nothing is ACKed; design 2 (connections) needs connection intervals that tolerate missed events (use larger intervals and supervision timeouts as the multi-connection guide suggests; coded PHY should keep `TX_RX_TLIM_EN`); design 3 (mesh, adv-bearer flooding) is the most sensitive and must drive `esp_coex_status_bit_set` for CONFIG/TRAFFIC/STANDBY.
- The only quantitative loss figure found (3 % → 20 %+ on an S3 with Wi-Fi/Matter) is consistent with ~50 % BLE air time plus collisions; no Espressif number exists, so any budget for "scan miss rate" must be measured on the target (sequence-numbered advertisements, fixed window=interval, Wi-Fi under HTTPS load).
- Configuration for this project: keep `ESP_COEX_SW_COEXIST_ENABLE=y` (default), pin controller + NimBLE host to one core and `ESP_WIFI_TASK_CORE_ID` to the other, keep Wi-Fi PS at the default `WIFI_PS_MIN_MODEM`, leave connectionless PS parameters at defaults; `esp_coex_preference_set(ESP_COEX_PREFER_BT)` still exists but is deprecated in 5.5.4.

### Gaps
- Espressif publishes no measured BLE latency, advertising delay distribution, scan miss rate, or Wi-Fi/HTTPS throughput numbers under coexistence for the ESP32-S3; the coexistence guide's only quantitative statements are the ≥100 ms period, 50/50 slicing, and the "1 in N" high-priority advertising event (N unspecified).
- The esp32.com threads with user measurements could not be fetched (bot-check); only search snippets were available.
- A search-snippet claim that the FAQ limits BLE scan interval to 0x100 slots when software coexistence is enabled was not found on the fetched FAQ page; unconfirmed.

## Key question 5: Known issues in ESP-IDF 5.4-5.5 for BLE on the ESP32-S3 (controller asserts, scan stalls, coexistence, memory)

### Takeaway
The 5.4.x/5.5.x patch releases each fixed several S3/C3 controller assertions (`lld_adv.c 2992`, `llc_llcp.c 487`, `sch_prog.c 304`, `lld_con.c 1479`), a "TX issue when the event is aborted", "missing ADV reports after bonding and connection", a "double free exception during BLE init under low memory", and (v5.5.4 itself) a NimBLE host flow-control bug introduced in v5.5.3 (only when `BT_NIMBLE_HS_FLOW_CTRL=y`, which is off by default on the S3). Still open in Oct 2026: BLE controller built with `CONFIG_BT_CTRL_RUN_IN_FLASH_ONLY=y` silently stops scanning/advertising on the S3 (#19297), worse under Wi-Fi/SPI load. The v5.5.2 scan-stops-after-hours regression (#18217) was ESP32-only (Bluedroid) and fixed in v5.5.3.

### Cited Findings
- v5.5.4 (27 Mar 2026): "Fixed the issue of potential NimBLE host connection loss in ESP-IDF v5.5.3 release on ESP32 / ESP32C3 / ESP32S3 (IDFGH-17350)" — https://github.com/espressif/esp-idf/releases/tag/v5.5.4 . ## Key question 6: Does enabling BLE force CONFIG_PM / light-sleep constraints or a 32 kHz clock?

### Takeaway
No. On the S3 the controller's modem sleep is off by default (`BT_CTRL_MODEM_SLEEP` default n); the low-power clock choice (main crystal / external 32 kHz / internal 136 kHz RC) only appears under modem-sleep mode 1, and all PM-lock code in `bt.c` is under `#ifdef CONFIG_PM_ENABLE`. The only forced setting is `ESP_WIFI_STA_DISCONNECTED_PM_ENABLE` (selected by `ESP_COEX_SW_COEXIST_ENABLE`), which this project already has on.

### Cited Findings
- `config BT_CTRL_MODEM_SLEEP bool "Bluetooth modem sleep" depends on !BT_CTRL_HCI_MODE_UART_H4 default n` — `components/bt/controller/esp32c3/Kconfig.in:380-386`; `BT_CTRL_MODEM_SLEEP_MODE_1` (default y, depends on MODEM_SLEEP): "bluetooth controller sleeps between and BLE events. A low power clock is used" — 388-395; `choice BT_CTRL_LOW_POWER_CLOCK depends on BT_CTRL_MODEM_SLEEP_MODE_1` with `BT_CTRL_LPCLK_SEL_MAIN_XTAL` ("Main crystal can be used as low power clock ... bluetooth modem sleep can work under Dynamic Frequency Scaling(DFS) enabled, and bluetooth can work under light sleep enabled"), `BT_CTRL_LPCLK_SEL_EXT_32K_XTAL` (depends on `RTC_CLK_SRC_EXT_CRYS || RTC_CLK_SRC_EXT_OSC`), `BT_CTRL_LPCLK_SEL_RTC_SLOW` ("accuracy ... larger than 500ppm ... don't select this option in scenarios such as BLE connection state") — 397-424; `BT_CTRL_MAIN_XTAL_PU_DURING_LIGHT_SLEEP` depends on `FREERTOS_USE_TICKLESS_IDLE` — 426-433. `CONFIG_BT_CTRL_SLEEP_MODE_EFF` is 0 unless MODEM_SLEEP_MODE_1 — 437-448.
- `BT_ENABLED` has no `select` of PM/tickless options: `config BT_ENABLED bool "Bluetooth" depends on !APP_NO_BLOBS` — `components/bt/Kconfig:3-7` (the only `select` in the top-level file is for `BT_RELEASE_IRAM`, which is ESP32-C2-only, lines 72-81).
- `bt.c`: `btdm_controller_enable_sleep(true)` only runs `if (s_lp_cntl.enable)` (bt.c:2097-2099), and the `no_light_sleep` PM-lock handling is under `#ifdef CONFIG_PM_ENABLE` (bt.c:2125-2126).
- `ESP_COEX_SW_COEXIST_ENABLE ... select ESP_WIFI_STA_DISCONNECTED_PM_ENABLE if (ESP_WIFI_ENABLED)` — `components/esp_coex/Kconfig:15`; `ESP_COEX_POWER_MANAGEMENT` default n — Kconfig:35-40. The Wi-Fi guide: "If CONFIG_ESP_WIFI_STA_DISCONNECTED_PM_ENABLE is enabled, RF, PHY and BB would be turned off in disconnected state when IDLE" and "it would be selected forcefully in Menuconfig at coexistence mode" — wifi.rst:2190-2192.
- Espressif's minimal NimBLE configs explicitly set `CONFIG_PM_ENABLE=n` — `bleprph/sdkconfig.defaults.mini:44,76`.

### Inferences
- With `PM_ENABLE=n` and no light sleep, BLE on the S3 keeps the controller fully awake between events (higher current, which is irrelevant for a mains/USB-powered display device) and needs no 32 kHz crystal; `BT_CTRL_MODEM_SLEEP` could later be enabled with `LPCLK_SEL_MAIN_XTAL` without hardware changes if power matters.

### Gaps
- None material; the v5.5.4 Kconfig and `bt.c` are explicit.
