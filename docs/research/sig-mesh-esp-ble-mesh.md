## Key question 1: How the mesh network layer delivers a message (bearer, flooding, TTL, cache, transmit/relay settings) and what latency that gives

### Takeaway
ESP-BLE-MESH sends every Network PDU as a non-connectable BLE legacy advertisement repeated `count+1` times at a `10*(steps+1)` ms interval (+10 ms random); the sender's single adv task is blocked for `copies * (interval + 10)` ms per message (90 ms with the examples' `ESP_BLE_MESH_TRANSMIT(2, 20)`), receivers scan continuously (20 ms window = 20 ms interval), and relaying is only attempted when TTL > 1 and the Relay feature is enabled, so a one-room network with TTL 0-1 is a single hop. Measured one-hop figures are 5-35 ms typical, with Espressif's own ESP32 request+response round trip mostly ~22 ms and worst case ~157 ms at 1 m.

### Inferences
- For 3-10 devices in one room all within radio range, set `send_ttl = 0` (or 1) and leave Relay disabled: every message is then exactly one adv burst, no relay storms, and the message cache only has to absorb the sender's own 1-3 copies. End-to-end latency is then dominated by (a) up to one adv interval + 10 ms random delay before the first copy (20-30 ms worst for the first copy, or immediate if the queue is empty), (b) the probability that the receiver's 20 ms scan window is on the channel being advertised (3 copies across 3 channels make this high), and (c) host processing. The Espressif 1-m measurement (~22 ms round trip typical, ~11 ms one way) and the nRF52 1-hop median of 4.5 ms both sit comfortably inside the 100-200 ms target; the outliers (157 ms RTT, 111 ms 1-hop max) are the risk, and they come from lost advertising events plus the 20-30 ms retransmit spacing.
- The adv task is serial: with `TRANSMIT(2, 20)` each outgoing Network PDU blocks the bearer for 90 ms, so a device can emit at most ~11 PDUs/s; with `TRANSMIT(0, 20)` it is 30 ms (~33 PDUs/s) but single-copy delivery is less reliable. Queue depth is `CONFIG_BLE_MESH_ADV_BUF_COUNT` (default 60, [Kconfig.in 828-838](file:///C:/Espressif/esp-idf/components/bt/esp_ble_mesh/Kconfig.in)); a backlog adds 90 ms per queued message to latency.
- Multi-hop is not needed for this demo, but if TTL > 1 and Relay were enabled on all nodes, the TI data (adding ~70-85 ms for the second hop with 4 relay copies at 10 ms) and the ESP defaults (3 relay copies at 20-30 ms) imply each relay hop costs roughly one relay burst (60-90 ms) plus a scan-window alignment, pushing a 2-hop path past the 200 ms target.

### Gaps
- No Espressif-published one-way latency figure for ESP32-S3 specifically; the vendor_models README numbers are from an ESP32 (chip not stated in the README, example predates S3) and are round trips.
- The exact random-delay implementation in the ESP32-S3 controller for the "+10 ms" is not documented in the stack sources read; the 10 ms is an assumed worst-case in `adv.c`.

## Key question 2: Provisioning: what must exist before nodes can talk, and how to do it with no phone app (provisioner in firmware vs. node provisioning itself with fixed keys)

### Takeaway
A node needs a NetKey (+ NetKey index), unicast address, IV index/flags and DevKey (provisioning) and then an AppKey bound to its models plus subscription/publication addresses (configuration). ESP-BLE-MESH has a full firmware Provisioner API (used by the `vendor_client`, `provisioner` and `fast_provisioning` examples), but the public node API has no "provision me with these keys" call: `esp_ble_mesh_node_add_local_net_key/app_key/bind_app_key_to_local_model` all return `-EIO NotProvisioned` unless the node is already provisioned. The only fixed-key self-provisioning path in v5.5.4 is the internal test API `bt_mesh_device_auto_enter_network()` (core/test.c, behind `CONFIG_BLE_MESH_SELF_TEST` + `CONFIG_BLE_MESH_TEST_AUTO_ENTER_NETWORK`), which wraps the Zephyr-style `bt_mesh_provision()` and also adds/binds an AppKey and subscribes every model to one group address; the core headers are on the public include path, so an application can call it, but it is documented as test-only.

## Key question 3: Models: Light HSL / Generic OnOff vs. a 4-byte vendor model; publish-to-group and subscribe; vendor payload limits; vendor_models example structure

### Takeaway
A vendor model with a 3-byte opcode and a 4-byte payload (R, G, B, holding) fits in one unsegmented PDU (8 bytes free after the opcode) and needs one model per device that both sends and receives; it can be addressed to a group (0xC000-0xFF00, needs a subscription on each receiver) or to the fixed all-nodes address 0xFFFF (delivered to every node's primary element without any subscription). - Simplest model design for this demo: one vendor model per device (same company id/model id on all), one opcode `STATE` with payload `{R, G, B, holding}` (4 of the 8 available bytes; add a 1-byte TID or sequence if you want duplicate suppression at the app level). ## Key question 5: Repeated state at a high rate: can a node publish every 100 ms while holding (period, cache, sequence numbers, IV update)?

### Takeaway
A 100 ms publish period is representable (publish period step = 100 ms) and the adv bearer can carry ~11 messages/s at `TRANSMIT(2,20)` (90 ms per message) or ~33/s at `TRANSMIT(0,20)`, so 10 Hz from one holder is feasible but near saturation with 3 copies, and with several simultaneous holders the per-device queues and the 10-entry message cache start to matter. Sequence numbers are 24-bit per node, one per Network PDU (retransmitted copies reuse it; publish-retransmits do not); ESP-BLE-MESH starts an IV Update when its own seq exceeds 8,000,000 (~222 h of continuous 10 Hz), but the spec-mandated 96 h minimum between IV states applies, and with `CONFIG_BLE_MESH_SETTINGS` on, the default `SEQ_STORE_RATE 0` writes the sequence number to NVS on every single message, which at 10 Hz is 10 flash writes/s unless you raise it.

### Inferences
- Budget at 10 Hz from one holder with `TRANSMIT(2,20)`: 900 ms of bearer time per second on the sender; the queue (60 buffers) absorbs bursts but latency grows 90 ms per queued message. Sending only on change (touch down / up / colour change) plus a slow 2-5 Hz keep-alive while holding would keep well inside the budget and still meet the 100-200 ms target. With 3 copies per message and 10 nodes holding at 10 Hz, each receiver sees up to 300 adv PDUs/s; the controller duplicate filter and the host message cache (10 entries, keyed src+seq) would then evict entries within ~30 ms, so raise `CONFIG_BLE_MESH_MSG_CACHE_SIZE` toward Zephyr's 32 if the rate is really sustained.
- Sequence-number arithmetic: 1 seq per message; 10 Hz continuous = 36,000/h, so the 8,000,000 IV-update trigger is reached after ~222 h and 2^24 after ~466 h of continuous transmission from one node. Real hold duty cycle is far lower, so exhaustion is not a demo-scale concern; but an IV Update cannot complete before the 96 h minimum in Normal state and both halves take at least 96 h each, so a node that really did burn 16.7M numbers in under 8 days would exhaust them (behaviour on wrap not guarded in `net.c`: no `0xFFFFFF` check found).
- With `CONFIG_BLE_MESH_SETTINGS=y` (needed for power-cycle survival, Q6), set `CONFIG_BLE_MESH_SEQ_STORE_RATE` to ~100-1000 and `CONFIG_BLE_MESH_STORE_TIMEOUT`/`RPL_STORE_TIMEOUT` to a few seconds; otherwise a 10 Hz sender performs an NVS write per message.
- Prefer Network Transmit copies over Publish Retransmit for reliability: the former reuse one seq number and one buffer, the latter spend a new seq and a new adv burst each.

## Key question 6: Robustness: power cycle (keys, sequence numbers, NVS, sequence restore) and a new device joining

### Takeaway
Without `CONFIG_BLE_MESH_SETTINGS` (default n) a node forgets everything at reset and must be provisioned again; with it, unicast address, NetKey, AppKey, IV index, RPL and the sequence number are restored from NVS, and the restored seq is rounded up to the next `SEQ_STORE_RATE` multiple so the node never reuses a number its peers have already seen (peers drop lower-or-equal seq as "Replay"). Locally injected keys/subscriptions (FAQ 1.16 method, test API) are not persisted. A new device joining with a provisioner is a PB-ADV exchange plus 3-4 Config Client messages; with self-provisioning it just needs a unique unicast address and the shared keys.

### Inferences
- Power-cycle scenario with a firmware provisioner: enable `CONFIG_BLE_MESH_SETTINGS` on all nodes (and on the provisioner, which also stores its node table) and a non-zero `SEQ_STORE_RATE`; then a rebooted node comes back provisioned with a higher seq and its messages are accepted immediately. Without SETTINGS, a rebooted node is unprovisioned, beacons every 5 s, and the provisioner must re-provision and re-configure it (while the old unicast address is still in the provisioner's table unless deleted with `esp_ble_mesh_provisioner_delete_node_with_addr`).
- Power-cycle scenario with fixed-key self-provisioning: the node re-enters the network instantly, but its seq restarts at 0 (`bt_mesh_provision`), so peers that stayed up keep RPL entries with the old (higher) seq and silently drop it as "Replay" until it catches up. Mitigations: keep your own seq in NVS and restore it with `bt_mesh_test_set_seq()` (test API) immediately after self-provisioning, or bump the IV index on every boot (peers accept IV index up to +42 via recovery and clear their RPL, per SiLabs/`net.c`), or let the stack's SETTINGS persist seq (it persists seq/IV for the self-provisioned node too; keys/bindings must be re-applied on boot since they are RAM-only).
- Joining with a new device: same keys, a unique unicast address (collision would make two nodes share an address and the RPL would drop one of them); the group/all-nodes addressing means existing devices need no change.

### Gaps
- Not verified whether `CONFIG_BLE_MESH_SETTINGS` restore marks a self-provisioned (test-API) node as provisioned on next boot without calling the test function again (the stack stores net/subnet/IV from `bt_mesh_provision`, so likely yes, but the AppKey/bindings are not stored).
- No measured figure for how long after an IV index bump peers take to accept the new index (beacon interval dependent).

## Key question 7: Practical complexity: code size/steps of the simplest node-to-node vendor example and known pitfalls (docs, GitHub 2024-2026, ESP32-S3)
