# Custom connectionless "advertising flood" over BLE with NimBLE on ESP32-S3 (ESP-IDF v5.5.4)

Scope: 3 (later 5-10) round-display ESP32-S3 devices in one room, each broadcasting "my RGB colour + I am holding" in non-connectable advertisements and scanning continuously; target touch-to-peer-update latency 100-200 ms; Wi-Fi STA stays connected. All local file references are the installed ESP-IDF v5.5.4 under `C:\Espressif\esp-idf\` (read directly). Web sources are marked; anything not verified against a primary source is flagged.

## Q1. Legacy advertising limits in NimBLE on ESP32-S3 (minimum interval, changing data while advertising)

### Takeaway
The NimBLE host in IDF v5.5.4 rejects `itvl_min` below 0x20 (20 ms) regardless of advertising type; the old pre-5.0 100 ms floor for ADV_NONCONN_IND is not enforced anywhere in the host, and the ESP32-S3 controller is documented as supporting the Bluetooth 5.0 "High Duty Cycle Non-Connectable Advertising" feature, so 20 ms non-connectable advertising is valid. Advertising data can be replaced while advertising with `ble_gap_adv_set_data` / `ble_gap_adv_set_fields`; the host performs no "is advertising" check and the HCI command is defined to take effect at the next advertising event.

### Cited Findings
- Host validation (`ble_gap_adv_validate`): `if (adv_params->itvl_min && (adv_params->itvl_min < 0x5) /* if BLE_HIGH_DUTY_ADV_ITVL */ ... else (adv_params->itvl_min < 0x20)) return BLE_HS_EINVAL;` and `if (adv_params->itvl_max && adv_params->itvl_max > 0x4000) return BLE_HS_EINVAL;` — [ble_gap.c:4140-4152](C:\Espressif\esp-idf\components\bt\host\nimble\nimble\nimble\host\src\ble_gap.c). Units are 0.625 ms (`BLE_HCI_ADV_ITVL (625) /* usecs */`, [hci_common.h:1751](C:\Espressif\esp-idf\components\bt\host\nimble\nimble\nimble\include\nimble\hci_common.h)), so 0x20 = 20 ms, 0x5 = 3.125 ms, 0x4000 = 10.24 s.
- The same validator also rejects `high_duty_cycle` for `BLE_GAP_CONN_MODE_NON` ("High duty cycle only allowed for directed advertising") and returns `BLE_HS_EALREADY` if `ble_gap_slave[0].op != BLE_GAP_OP_NULL` (already advertising) — [ble_gap.c:4136-4160](C:\Espressif\esp-idf\components\bt\host\nimble\nimble\nimble\host\src\ble_gap.c).

- The ESP32-S3 controller is shipped as a prebuilt library under `components/bt/controller/lib_esp32c3_family/esp32s3/` (Link Layer source not available for inspection) — verified by directory listing (see final report).

### Inferences
- Use `BLE_GAP_CONN_MODE_NON` + `BLE_GAP_DISC_MODE_NON` (or `GEN`, see Q6), `itvl_min = itvl_max = BLE_GAP_ADV_ITVL_MS(20)` = 0x20; this passes `ble_gap_adv_validate` and matches the BT 5.0 feature the S3 controller is documented to support. Going below 20 ms needs `CONFIG_BT_NIMBLE_HIGH_DUTY_ADV_ITVL=y`; whether the S3 controller accepts e.g. 0x10 is unverified (the option exists for Espressif controllers, which suggests it does).
- Changing *data* while advertising: call `ble_gap_adv_set_data()` with a prebuilt 31-byte buffer (cheaper than `set_fields`); no stop/start. Changing the *interval* requires `ble_gap_adv_stop()` then `ble_gap_adv_start()` because the interval lives in LE Set Advertising Parameters (the Core spec disallows that command while advertising is enabled; recalled, not verified here).
- The old `BLE_HCI_ADV_ITVL_NONCONN_MIN` constant is dead code in this host version; do not rely on the host to warn you about the pre-5.0 rule.

### Gaps
- No readable controller source: whether the S3 controller returns an HCI error for non-connectable intervals < 0x20 when HIGH_DUTY is enabled is unverified. Test with `ble_gap_adv_start()` return code.
- Exact Core Spec 5.0 change text (Vol 6 Part B 4.4.2.2) could not be fetched from the SIG; the 100 ms -> 20 ms change is supported only by vendor/secondary sources above plus Espressif's feature table naming the 5.0 feature.

## Q2. Extended advertising (BLE 5.0, CONFIG_BT_NIMBLE_EXT_ADV): limits and whether it is worth it

### Takeaway
Extended advertising on ESP32-S3 allows 251 bytes per HCI data command and up to 1650 bytes total per advertising set (Kconfig `BT_NIMBLE_EXT_ADV_MAX_SIZE` 0-1650), up to 4 instances, but enabling it removes the legacy API, moves reports to `BLE_GAP_EVENT_EXT_DISC`, and makes every receive a two-PDU affair (ADV_EXT_IND on 37/38/39 pointing to AUX_ADV_IND on a data channel). For a payload of ~7 bytes per device the 27 usable bytes of a legacy manufacturer-data PDU are sufficient; extended advertising is not worth it for this demo.

### Inferences
- Payload need: per device {id 1, seq 1, ttl/hops 1, flags 1, RGB 3} = 7 bytes; own state plus two relayed neighbours = 21 bytes + 2-byte company ID + 2-byte AD header = 25 <= 31. Legacy suffices even with relaying.
- Cost of ext adv for this use: each reception needs ADV_EXT_IND then a hop to the AUX channel, so a scanner is busy longer per packet and can miss other primaries meanwhile; phones' legacy scanners (useful for debugging with nRF Connect) would not show the data unless they support ext scan; the whole legacy API disappears from the build.
- One legitimate ext-adv use: `legacy_pdu=1` through `ble_gap_ext_adv_*` to get several *independent legacy* instances (e.g. one at 20 ms for "my state", one at 500 ms for a relay digest) with their own random addresses, if ever needed. Not needed initially.

### Gaps
- The controller's advertised `Max_Advertising_Data_Length` (HCI LE Read Maximum Advertising Data Length) for ESP32-S3 was not found in docs; the 1650 figure comes from Espressif's generic doc and the host Kconfig range.

## Q3. Scanning: interval/window, passive vs active, filter_duplicates, controller duplicate filter, report flow control, how a report reaches the app, advertise + scan simultaneously

### Takeaway
`ble_gap_disc()` with `passive=1`, `filter_duplicates=0`, `itvl == window` (units 0.625 ms, min 4, max 0x4000, window <= itvl enforced) and `BLE_HS_FOREVER` gives near-continuous listening; `filter_duplicates` maps straight to the HCI `LE Set Scan Enable` Filter_Duplicates bit and must be 0 (or the controller filter type must be DATA_DEVICE) for state updates from the same address to be reported. Reports arrive as `BLE_GAP_EVENT_DISC` with `struct ble_gap_disc_desc {event_type, length_data, addr, rssi, data}` in the NimBLE host task. The controller discards reports beyond `BT_CTRL_BLE_ADV_REPORT_FLOW_CTRL_NUM` (100) unprocessed ones and the host in v5.5.4 does not surface the "adv lost" vendor event to the app. Advertising and scanning run concurrently on the S3 (the host treats them as independent slave/master ops; Espressif's coexistence table lists BLE scan and advertising as supported with Wi-Fi STA connected), but the interleaving policy inside the closed-source controller is not documented.

## Q4. Reliability maths and expected latency (N advertisers, interval T, 3 channels, continuous scanner)

### Takeaway
Published models treat advertising as slotted/unslotted ALOHA: the probability that one PDU survives N-1 other advertisers of load rho = tau/T each is roughly (1 - 2 rho)^(N-1) ~ e^(-2 rho (N-1)). With a 47-octet on-air legacy PDU (376 us at 1 Mb/s) and 10 devices at 20 ms, the idealised per-event loss is ~24% (12% at 50 ms, 6% at 100 ms), and the first advertising event after a change lands within T + 10 ms (advDelay). Combining both, a 20 ms interval reaches all 9 peers with 99% probability within ~150 ms worst case; 50 ms needs ~240 ms; 100 ms needs ~330 ms. Measured large deployments show collision rates of 0.22-0.33 with >200 tags, the capture effect adds a few percent, and Wi-Fi interference can multiply loss by 4.

### Cited Findings
- Collision model: "The probability that an arbitrary advertisement is successful is given by P{SAA} = (1-2 rho_A)^(N_A-1) ~ e^(-2 rho_A (N_A-1))", each collision destroys both packets; successive collisions are correlated, which raises scanning-job failure — [NSF-hosted paper (search snippet; fetch refused)](https://par.nsf.gov/servlets/purl/10275622); companion thesis G. Humphrey, "Simulation Analysis Of Bluetooth Scanning Systems", Univ. of Mississippi 2020: interadvertisement time = fixed interval + pseudo-random delay; collision probability on successive advertisements does not depend on the interadvertisement time; failure probability "not excessively sensitive to interadvertisement time" — [eGrove ETD 1823](https://egrove.olemiss.edu/etd/1823).
- advDelay: "The BLE specification adds a random delay of 0-10 ms to each interval ... This randomization is mandatory and cannot be disabled"; each event sends the same PDU "on all three channels sequentially, with ~150 us between transmissions"; packet = 1-byte preamble + 4-byte access address + PDU with "up to 37 bytes of payload", 6 of which are the advertiser address, leaving 31 — [applied-ee BLE Advertising & GAP](https://applied-ee.github.io/embedded/docs/networking/bluetooth-ble/ble-advertising-gap/). Nordic forum: T_advEvent = advInterval + advDelay — [Nordic DevZone 12329](https://devzone.nordicsemi.com/f/nordic-q-a/12329/beacon-advertising-with-20msec-interval).
- On-air size: a 38-byte advertising PDU is "46-47 octets on air in the 1 and 2 Mbps modes" (preamble + access address + CRC overhead) — [BlueFlood, ar5iv 2002.12906](https://ar5iv.arxiv.org/html/2002.12906).
- Rondón et al., "Understanding the Performance of Bluetooth Mesh" (arXiv 1910.03345): T_interPDU between the three channel transmissions "of up to 10 ms"; with T_interPDU 8-10 ms and ScanInterval 20 ms success was "below 20%", with T_interPDU 1-2 ms and ScanInterval 10 ms near 100%; "if ScanWindow equals ScanInterval, the device scans continuously"; WLAN interference made afternoon loss "more than 4 times" the morning level and channel 37 (overlapping WLAN channel 1) lost most; end-to-end delay "around 250 ms for over 10 hops" in the worst simulated case; a single source replica cut loss "up to 25%"; one replica per relay adds congestion; recommendation to randomise T_interPDU and back-off and to match ScanInterval to the advertising structure — [ar5iv 1910.03345](https://ar5iv.labs.arxiv.org/html/1910.03345). Note: this is simulation (per the search summary, [arXiv abs](https://arxiv.org/abs/1910.03345v1)).
- Nikodem & Bawiec, "Experimental Evaluation of Advertisement-Based Bluetooth Low Energy Communication" (Sensors 2019/2020, >200 tags to one hub): "Even with collision rates of 0.22 to 0.33, repeated advertisement transmissions keep reception rates acceptable" — [Semantic Scholar record](https://api.semanticscholar.org/graph/v1/paper/DOI:10.3390/s20010107?fields=title,abstract,authors,year,venue,citationCount) (abstract only; PMC/MDPI pages blocked).
- Molina et al., "Be aware of the capture effect: a measure of its contribution to BLE advertisements reception" (WONS 2021): Faraday-box tests with 2-14 advertisers; at 14 devices the capture effect raised delivery by 2.95% on average, 7.8% peak; simulations up to 1000 advertisers show up to +25% PDR — [HAL record](https://hal-imt-atlantique.archives-ouvertes.fr/hal-03165168) (search summary; full text blocked), [dblp](https://dblp.uni-trier.de/rec/conf/wons/MolinaBCB21.html).
- BlueFlood (concurrent-transmission flooding with non-connectable beacons, nRF52, 2 Mbps): "99.9% end-to-end delivery ratio with a duty-cycle of 0.4%" for 38-byte advertisements every 200 ms; capture of *different* data needs "a power delta of roughly 6 dB or more" — [ar5iv 2002.12906](https://ar5iv.arxiv.org/html/2002.12906). (Requires sub-microsecond slot sync; not reproducible with a stock HCI controller — inference.)
- Older ESP32 NimBLE report: continuous passive scan (30 ms/30 ms) silently stopped delivering `ble_gap_disc` callbacks after hours, faster (~10-15 min) with ~50 advertisements/s; fixed in the controller (commit 2f6f842, July 2020, ESP32-PICO-D4) — [esp-idf #4196](https://github.com/espressif/esp-idf/issues/4196).

### Inferences
Model used (idealised, single room, all in range, no Wi-Fi loss):
- tau = on-air time of one PDU. Full legacy PDU: 2 header + 6 AdvA + 31 AdvData = 39 B PDU; +1 preamble +4 AA +3 CRC = 47 octets = 376 us at 1 Mb/s. Compact 12-byte AdvData: 28 octets = 224 us.
- T_eff = interval + 5 ms (mean advDelay). rho = tau / T_eff. P_rx per advertising event ~ (1 - 2 rho)^(N-1); (N-1) conservatively also covers the receiver's own transmit time (it cannot hear while sending its own event).
- Per-event loss p (tau = 376 us):

| interval | T_eff | N=3 | N=5 | N=10 |
|---|---|---|---|---|
| 20 ms | 25 ms | 5.9% | 11.5% | 24% |
| 50 ms | 55 ms | 2.7% | 5.4% | 11.7% |
| 100 ms | 105 ms | 1.4% | 2.8% | 6.3% |

- Latency of the *first* event after a state change (uniform phase + advDelay): max interval + 10 ms, mean interval/2 + 5 ms -> 30/15 ms at 20 ms, 60/30 ms at 50 ms, 110/55 ms at 100 ms.
- Worst-case time until *all* N-1 peers have received the new state with >= 99% probability, k events with (1 - p^k)^(N-1) >= 0.99, bound k x (interval + 10 ms):

| interval | N=3 | N=5 | N=10 |
|---|---|---|---|
| 20 ms | 2 events, 60 ms | 3 events, 90 ms | 5 events, 150 ms |
| 50 ms | 2 events, 120 ms | 3 events, 180 ms | 4 events, 240 ms |
| 100 ms | 2 events, 220 ms | 2 events, 220 ms | 3 events, 330 ms |

- Channel occupancy per advertising channel at 10 devices / 20 ms: 10 x 0.376 / 25 = 15% — modest; the dominant loss is pairwise overlap, not saturation.
- Real-world factors not in the model: Wi-Fi STA traffic on the same radio (coexistence pre-empts all but "one in N" advertising events during Wi-Fi slices, and steals scan time), 2.4 GHz interference on channel 37 (Rondón), and controller-side report discard under host overload. Expect measured loss 1.5-3x the table; the 20 ms + continuous passive scan configuration still leaves margin for the 100-200 ms target with 3-10 devices; 100 ms steady-state advertising is adequate for keepalive but not for the latency target at 10 devices.
- Because the scanner dwells on one channel at a time, the three-channel repetition inside an event gives one reception opportunity per event per scanner, not three; it is the *per-event* loss above that matters, and the only way to add diversity is more events (shorter interval or a burst after a change).

### Gaps
- No measurement of ESP32-S3-specific advertising-event duration (gap between channel 37/38/39 PDUs) or scan-channel rotation; the model assumes the event fits inside one scan dwell.
- The NSF-hosted collision paper and the capture-effect paper could only be read through search summaries; the formula is quoted from the snippet.
- No source quantifies Wi-Fi-connected scan duty loss on the S3 (left to the Wi-Fi coexistence researcher).

## Q5. Relay / flooding over advertising: TTL, sequence numbers, dedupe cache, SIG mesh reference pattern

### Takeaway
Bluetooth Mesh is the reference: every network PDU carries a 24-bit SEQ per source and a TTL (max 127); a node relays only if the PDU authenticates, is not in its message cache, and TTL >= 2, after decrementing TTL; Network Transmit sends each original 1 + count times (Zephyr default 2 extra, 20 ms apart with a 0-10 ms random component) and Relay Retransmit repeats each relayed copy (default 2 extra at 20 ms); the message cache keyed on (source, sequence) suppresses duplicate storms. Trickle (RFC 6206) adds the suppression rule "do not transmit if you already heard k consistent copies in this interval". In a one-room demo where every node hears every other, relaying should be present in the packet format (hop/TTL byte) but disabled (TTL = 0) until a device actually needs it.

### Cited Findings
- Zephyr mesh Kconfig (primary implementation defaults): `BT_MESH_NETWORK_TRANSMIT_COUNT` default 2, range 0-7 ("initial number of retransmissions of original messages, in addition to the first transmission"); `BT_MESH_NETWORK_TRANSMIT_INTERVAL` default 20 ms, range 10-330; `BT_MESH_RELAY_RETRANSMIT_COUNT` default 2; `BT_MESH_RELAY_RETRANSMIT_INTERVAL` default 20 ms; `BT_MESH_MSG_CACHE_SIZE` default 32 ("how many recently seen messages the node caches so it can ignore duplicates"; too low -> extra traffic, too high -> processing time/RAM); `BT_MESH_RELAY_BUF_COUNT` default 32; `BT_MESH_ADV_BUF_COUNT` default 6; `BT_MESH_DELAYABLE_PUBLICATION` delays periodic publications by a random 20-50 ms "to reduce collisions when many nodes publish at once" — [Zephyr subsys/bluetooth/mesh/Kconfig](https://raw.githubusercontent.com/zephyrproject-rtos/zephyr/main/subsys/bluetooth/mesh/Kconfig).
- Silicon Labs mesh API (spec formulas): network transmit "The interval between transmissions is a random value between 10*(1+steps) and 10*(2+steps) milliseconds", count "Number of network layer transmissions beyond the initial one. Range: 0-7", steps range 0-31; relay retransmit interval 10*(1+steps) ms, count 0-7; deprecated adv/scan defaults: adv_interval_min/max 32 (20 ms), scan_interval 160 (100 ms), all 3 channels, random address — [Silabs sl_btmesh_test](https://docs.silabs.com/btmesh/7.0.1/bluetooth-mesh-api/sl-btmesh-test).
- Mesh relay rule (secondary): a relay retransmits only if the packet "authenticates against a known network key", "is not in message cache", and "has a TTL >= 2", sending with "TTL = TTL - 1"; max TTL 127; "Message caching is used to prevent relaying recently seen messages"; "Each message has a sequence number that protects the network against replay attacks" — [Wikipedia: Bluetooth mesh networking](https://en.wikipedia.org/wiki/Bluetooth_mesh_networking).
- Flooding drawbacks: Rondón et al. — "scalability is especially challenging because the protocol is prone to broadcast storms"; randomising timing parameters and varying advertising event duration reduces the drawbacks; one replica per relay adds congestion while a single source replica is viable — [arXiv 1910.03345](https://arxiv.org/abs/1910.03345v1), [ar5iv](https://ar5iv.labs.arxiv.org/html/1910.03345). A routing-vs-flooding simulation reports flooding "consumes about ten times more power because of redundant messages" — [arXiv 2208.04050](https://arxiv.org/pdf/2208.04050) (search summary).
- Trickle (RFC 6206): parameters Imin, Imax (number of doublings), k; at each interval start c = 0 and t is random in [I/2, I); hearing a consistent message increments c; at t transmit only if c < k; interval doubles up to Imax; on an inconsistent message reset I to Imin; typical k 1-5, "high value such as 5 or 10 is preferable to disabling suppression" — [RFC 6206](https://www.rfc-editor.org/rfc/rfc6206.html).
- NimBLE host side: the host's mesh port runs a separate advertising thread "which keeps on feeding advertisement events to the main thread" — [nimble/index.rst:25](C:\Espressif\esp-idf\docs\en\api-reference\bluetooth\nimble\index.rst) (an indication that heavy advertising-data churn is expected to be driven from a dedicated task).

### Inferences (design rules for the custom protocol)
- Per-source sequence number: 8 bits is enough at <= 50 packets/s if receivers compare with wrap-around arithmetic ((int8_t)(new - old) > 0) and reset the per-peer state after expiry; 16 bits removes the ambiguity if relays can delay copies by > 2.5 s. Bump SEQ only when the state changes *or* every K-th repeat if the DATA_DEVICE controller filter is used (Q3) so repeats still pass the filter.
- Dedupe cache: table keyed by origin id -> last SEQ seen + timestamp (N <= 16 entries); accept if newer; drop otherwise. This also dedupes the second copy you may get when the scanner switches channel in the middle of a peer's 3-channel event.
- Relay with TTL: hops byte = remaining TTL (0 = do not relay). Relay only if not already seen and TTL >= 1, decrement, send once after a random 10-30 ms delay (SIG step-1 timing), and suppress the relay if a copy from any other relay was heard during the delay (Trickle k = 1). Never relay more than once per (origin, SEQ). Relay copies carry the *origin's* id in the payload because `AdvA` will be the relay's address.
- Expiry: a peer's "holding" state is level-based and refreshed every advertising event, so the keepalive is implicit; expire the peer (treat as not holding) after ~3 x its steady-state interval + 100 ms (e.g. 400-500 ms with a 100 ms steady interval); releases are normally seen immediately via the next packet carrying holding = 0 (within interval + 10 ms), expiry only covers a lost release.
- Adaptive interval ("burst then settle", Trickle-like): on any local state change set 20 ms for ~300 ms (about 10 events, giving >= 5 reception opportunities to every peer at N = 10), then 100 ms steady state. Requires adv stop/start to change the interval (Q1) — ~2 HCI commands; alternatively keep 20 ms permanently for <= 5 devices.

## Q6. Payload design: manufacturer-specific AD type 0xFF, what else must be in the PDU, NimBLE field API

### Takeaway

### Inferences
- Proposed AdvData (<= 31 B): `[len][0xFF][company_lo][company_hi][proto_ver/type 1][origin_id 1][seq 1][ttl 1][flags 1: bit0 holding][R][G][B]` = 12 B AdvData for own state; optional relayed entries of 7 B each ({origin_id, seq, ttl, flags, R, G, B}) up to 2 more (26 B). `origin_id` can be the low byte of the device's BLE address (collision check at boot by listening for 1 s) or a configured 1-byte id; the direct sender is always identifiable from `desc->addr`.
- Do not include Flags, Name, or TX-power AD types; they only cost bytes. Use `disc_mode = BLE_GAP_DISC_MODE_NON` (no Flags needed) — the host accepts `disc_mode < BLE_GAP_DISC_MODE_MAX`.
- Build the 31-byte buffer once per state change and call `ble_gap_adv_set_data(buf, len)` directly (skip the fields serialiser); parse on receive with `ble_hs_adv_find_field(0xFF, desc->data, desc->length_data, &f)` and check `f->length >= 2 + 8` and the company ID before trusting the bytes.
- Company ID: 0xFFFF is reserved by the Bluetooth SIG for internal use / testing and Espressif's assigned ID is 0x02E5 — both are recalled from the Assigned Numbers document and were not re-verified in this session; for a private demo either works since you also check a protocol byte.

### Gaps
- Assigned-numbers confirmation for 0xFFFF / 0x02E5 not fetched.
- The Core Specification Supplement wording that Flags "may be omitted" for non-connectable, non-discoverable advertising was not fetched; the NimBLE code comment and observer-mode behaviour are the practical confirmation.

## Q7. Address / identity: using the BLE address as the peer id, NimBLE address types, privacy off

### Takeaway
Call `ble_hs_util_ensure_addr(0)` (prefer public; falls back to a random static address) and `ble_hs_id_infer_auto(0, &own_addr_type)` (privacy = 0 -> `BLE_OWN_ADDR_PUBLIC` if a public address exists, else random static); then advertise with that `own_addr_type`. ## Q8. Known pitfalls on ESP32-S3 + IDF 5.x NimBLE for continuous scanning + advertising

### Takeaway
The documented failure modes are (1) silent controller-side discard of advertising reports once 100 are queued, with no NimBLE app callback for the vendor "adv lost" event; (2) controller memory exhaustion when scanning with duplicate filtering off and a slow callback (mitigated by `BT_NIMBLE_HOST_QUEUE_CONG_CHECK`); (3) continuous scanning starving Wi-Fi (DHCP/association failures reported with default 30/30 ms windows on older IDF) and Wi-Fi pre-empting all but one-in-N advertising events; (4) a historical controller bug where continuous scanning stopped after hours at high advertising rates (fixed 2020). No ESP32-S3-specific NimBLE scan-stall issue from 2023-2026 was found.

- Report discard and threshold: `BT_CTRL_BLE_ADV_REPORT_FLOW_CTRL_NUM` default 100, `..._DISCARD_THRSHOLD` default 20, "If you set BT_CTRL_BLE_ADV_REPORT_DISCARD_THRSHOLD to a small value or printf every adv lost event, it may cause adv packets lost more" — [esp32c3/Kconfig.in:241-264](C:\Espressif\esp-idf\components\bt\controller\esp32c3\Kconfig.in). ## Summary of design rules for the custom advertising flood (synthesis of the above)
1. Advertising: `BLE_GAP_CONN_MODE_NON`, `BLE_GAP_DISC_MODE_NON`, `itvl_min = itvl_max = 0x20` (20 ms) during the ~300 ms after a change, 0xA0 (100 ms) steady; change data with `ble_gap_adv_set_data()` without restarting; restart only to change the interval.
2. Scanning: `ble_gap_disc(own_addr_type, BLE_HS_FOREVER, {itvl = window = 80-160 (50-100 ms), passive = 1, filter_duplicates = 0})`; dedupe and expiry in software.
3. Payload: single 0xFF AD structure, company ID + protocol byte + {origin, seq, ttl, flags, RGB} (7 B) + up to 2 relayed entries; <= 31 B; no Flags/Name.
4. Identity: public/random-static address as peer key, privacy off; 1-byte origin id in payload for relayed entries.
5. Dedupe: per-origin last-SEQ table with timestamps; accept only newer SEQ; expire after ~3 steady intervals + 100 ms.
6. Relay (optional, off by default in one room): TTL byte, relay once after a random 10-30 ms delay, suppress if another relay copy was heard, decrement TTL, never relay your own or already-seen (origin, SEQ).
7. Expected performance (idealised model, N = 10, 20 ms burst): first update within 30 ms, all peers within ~150 ms at 99%; at 100 ms steady state a single event reaches a given peer with ~94% and all peers within ~330 ms — so the 20 ms burst on change is what meets the 100-200 ms target.
