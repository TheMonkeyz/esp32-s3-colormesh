## KQ1. NimBLE on ESP32-S3: maximum concurrent connections, Kconfig ranges/defaults, per-connection cost, simultaneous central + peripheral, what `ble_multi_conn` demonstrates, and whether a device can keep N links while still advertising/scanning

### Takeaway
On the ESP32-S3 the NimBLE host allows at most 9 concurrent connections (`CONFIG_BT_NIMBLE_MAX_CONNECTIONS` range 1-9, default 3) and the controller allows at most 10 "activities" in total (`CONFIG_BT_CTRL_BLE_MAX_ACT` range 1-10, default 6, 828 bytes each), where every connection, the scanner and each advertising set each consume one activity, so "9 links + still advertising" needs MAX_ACT = 10 and "9 links + advertise + scan" does not fit. All four GAP roles are compiled in by default and one device can be central on some links and peripheral on others, but the `ble_multi_conn` example that the brief points at does NOT build for the ESP32-S3 (it needs vendor HCI commands only present in the C5/C6/C61/H2 controllers); the S3-capable multi-role example is `ble_gattc_gatts_coex`.

Help text: "For ESP32-C3 or ESP32-S3, user is expected to configure BT_CTRL_BLE_MAX_ACT from controller menu. For ESP32C2, ESP32C6 and ESP32H2, each connection will take about 1k DRAM." (no per-connection host figure is given for the S3) — `NIMBLE_KCONFIG` lines 275-289.

### Inferences
- Activity budget on the S3: with `MAX_ACT = 10` (max), a device can hold 9 connections plus one more activity (either the scanner or one advertising set). A symmetric "every device stays discoverable AND keeps scanning" design therefore caps at 8 connections per device (8 + adv + scan = 10). For the 3-device demo (2 links each) the default `MAX_ACT = 6` and `MAX_CONNECTIONS = 3` already suffice; for 10 devices in a full mesh (9 links each) set `MAX_CONNECTIONS = 9` and `MAX_ACT = 10`, and stop scanning once all peers are linked.
- Simultaneous roles are a controller feature on the S3 (BLE 4.1-style multi-role); the host simply tracks each link with its own GAP callback, as both examples show. The restrictions are procedural, not topological: only one outgoing connection attempt at a time, and (by default) scanning must be paused during the attempt. Advertising is not checked by `ble_gap_connect()` (no `ble_gap_adv_active()` test in `BLE_GAP_C` lines 8071-8105), so a device can advertise while it initiates.
- Legacy connectable advertising ends when a central connects to it (which is why the peripheral example restarts advertising in `BLE_GAP_EVENT_CONNECT`), so "still discoverable while connected" means restarting advertising after each incoming link until the connection cap is reached.
- Because the vendor "common factor" scheduling of `ble_multi_conn` is unavailable on the S3, multiple S3 links are scheduled by the closed controller with no application control over connection-event alignment; the Multi-Connection Guide's advice (raise the interval as links grow) is the only official lever.

### Gaps
- No per-connection host RAM figure for the S3 in the Kconfig help (only "about 1k DRAM" for C2/C6/H2) and no measured heap-per-link number for NimBLE on the S3 was found; the controller figure is 828 bytes per activity.
- No Espressif statement was found on how the ESP32-S3 controller schedules N links (event alignment, what happens when events collide); the only Espressif scheduling guidance is in the C6/H2 vendor-API example.
- The full text of NimBLE-Arduino #1160 does not resolve whether `BT_CTRL_BLE_MAX_ACT` was the second limit; it is an Arduino-build problem, not an IDF v5.5.4 observation.

## KQ2. Connection parameters: minimum interval, sensible intervals with 2-9 links under Wi-Fi coexistence, notification latency and throughput for 4-byte notifications, supervision timeout, reconnection time, and "drops when Wi-Fi is busy" reports

### Takeaway
The spec floor is a 7.5 ms interval and a 100 ms supervision timeout; NimBLE's defaults when you pass no parameters are 30-50 ms interval, latency 0 and a 2.56 s supervision timeout. Espressif's only multi-link guidance is "about 5 ms of air time per link, interval = links x 5 ms, timeout = 30 x interval" and a formula that for 9 small-packet links allows intervals well under 10 ms in theory; but with Wi-Fi connected the radio is time-sliced roughly 50/50 in periods of "more than 100 ms", and ESP32-S3 users report supervision-timeout drops under Wi-Fi load that were cured by `WIFI_PS_MIN_MODEM` and longer timeouts. No measured per-notification latency for the S3 was found.

### Cited Findings
- Connection interval: "step size ... 1.25 ms, with a range from 7.5 ms (6 steps) to 4.0 s (3200 steps)"; in each connection event "the central device first sends a packet to the peripheral device, followed by a packet from the peripheral device back ... Even if either party does not need to send data at the start of a connection interval, it must send an empty packet to maintain the connection"; if the data does not fit "the next packet exchange must wait until the next connection interval begins" — `C:\Espressif\esp-idf\docs\en\api-guides\ble\get-started\ble-connection.rst` lines 41-54. HCI constants: `BLE_HCI_CONN_ITVL 1250 us`, `BLE_HCI_CONN_ITVL_MIN 0x0006`, `MAX 0x0c80`, `BLE_HCI_CONN_LATENCY_MAX 0x01f3`, `BLE_HCI_CONN_SPVN_TIMEOUT_MIN 0x000a` (100 ms), `MAX 0x0c80` (32 s), units 10 ms — `HCI_COMMON_H` lines 1805-1815.
- Supervision timeout: "the maximum time allowed between two successful connection events ... if one party unexpectedly loses power or moves out of range, the other party can determine whether to disconnect" — `ble-connection.rst` line 68. Peripheral latency: "maximum number of connection events that the peripheral device can skip when there is no data to send" — line 74.
- NimBLE defaults applied when `ble_gap_connect()` gets `NULL` params: `BLE_GAP_INITIAL_CONN_ITVL_MIN = 30 ms`, `..._MAX = 50 ms`, latency 0, `BLE_GAP_INITIAL_SUPERVISION_TIMEOUT 0x0100` (256 x 10 ms = 2560 ms), CE length 0 — `BLE_GAP_H` lines 113-124; the S3-capable example's log confirms "itvl_min=24 itvl_max=40 ... supervision_timeout=256" and "scan_itvl=16 scan_window=16" (10 ms) — `ble_gattc_gatts_coex\README.md` line 67. Helper macros `BLE_GAP_CONN_ITVL_MS(t)`, `BLE_GAP_SUPERVISION_TIMEOUT_MS(t)` — `BLE_GAP_H` lines 50-51.
- Espressif multi-link parameter rule (C6/H2 example, written for the vendor scheduler): "set the connection interval as an integer multiple of the MINIMUM_CONN_INTERVAL ... MINIMUM_CONN_INTERVAL > ((MAX_TIME_OF_PDU * 2) + 150us) * CONN_NUM. For example, if we have 10 connections, maximum TX/RX length is 251 and the phy is 1M, then the MINIMUM_CONN_INTERVAL should be greater than ((261 * 8us) * 2 + 150us) * 10 = 43260us." — `MULTI_CENT` lines 394-405; the example reserves 5 ms per link and uses interval = peers x 5 ms, supervision = 30 x interval — lines 18-20, 346.
- Throughput reference (NimBLE, two ESP32 boards, 60 s, MTU 512, conn itvl 7.5 ms, DLE 251, 1M PHY): NOTIFY ~340 kbps, READ ~200 kbps, WRITE ~500 kbps; "Connection Interval: The default is 7.5ms (minimum allowed by BLE spec)"; 2M PHY "can double the air data rate" on BLE 5 chips; 50 MSYS blocks used — `C:\Espressif\esp-idf\examples\bluetooth\nimble\throughput_app\README.md` lines 9-37.
- Coexistence time slicing (S3 has Wi-Fi + BLE only): "Wi-Fi and BLE have their fixed time slice to use the RF ... CONNECTED status: the coexistence period starts at the Target Beacon Transmission Time (TBTT) and is more than 100 ms ... the scenario of Wi-Fi CONNECTED and BLE CONNECTED has a corresponding coexistence scheme. In this scheme, the time slices of Wi-Fi and BLE in a coexistence period each account for 50%." — `COEXIST_RST` lines 183-203. Dynamic priority: "in every N BLE Advertising events, there is always one event with high priority. If a high-priority BLE Advertising event occurs within the Wi-Fi time slice, the right to use the RF may be preempted by BLE." — line 214. "in coexist mode, Wi-Fi will remain active only during Wi-Fi time slice, and sleep during non Wi-Fi time slice even if `esp_wifi_set_ps(WIFI_PS_NONE)` is called" — `WIFI_RST` line 2172. Default Wi-Fi power save is `WIFI_PS_MIN_MODEM` — line 2174.
- "Drops when Wi-Fi is busy" (secondary; esp32.com pages were behind a bot check so only search excerpts were readable): an ESP32-S3 + NimBLE + MQTT user saw the BLE link drop "about 9 times over night" with `BLE_ERR_CONN_SPVN_TMO` at a 300 ms interval and 1300 ms supervision timeout; setting Wi-Fi power save to `WIFI_PS_MIN_MODEM` made the Wi-Fi link stable and "increasing the supervision timeout helps when wifi is stable" — [esp32.com "Wifi Ble Coex stability" (late 2024)](https://esp32.com/viewtopic.php?p=140266). A second thread found a central "skipped empty connection-interval packets for several intervals", dropping the peripheral; longer supervision timeouts reduced drops (16 s/4 s often, 10.5 s/1.5 s less, "32 s / 2 s has not disconnected in 3 days, but is an impractical value") — [esp32.com "WiFi BLE coexistence adjustment for BLE disconnect"](https://esp32.com/viewtopic.php?p=146737). Espressif's coexistence page also recommends pinning the Wi-Fi and NimBLE tasks to different cores (`CONFIG_BT_NIMBLE_PINNED_TO_CORE_CHOICE`) — [docs.espressif.com RF Coexistence (esp32s3)](https://docs.espressif.com/projects/esp-idf/en/stable/esp32s3/api-guides/coexist.html) (search excerpt; the option exists locally at `NIMBLE_KCONFIG` lines 37-47).
- Reconnection behaviour in the examples: on `BLE_GAP_EVENT_DISCONNECT` the central deletes the peer and resumes scanning, the peripheral resumes advertising — `MULTI_CENT` lines 120-133, `MULTI_PRPH` lines 208-214, `COEX_MAIN` lines 326-336, 394-397. Connection-establishment times in the logs: C6/H2 example with 300 ms adv interval and 500/200 ms scan interval/window: 0.62-0.95 s from "Create connection" to "Connection established" per link (README lines 43-70; parameters at `MULTI_CENT` lines 243-244, 286-291); S3-capable example with 10 ms scan interval/window: 140 ms (log 489 ms → 629 ms, README lines 64-70). Boot-to-host-ready in those logs: "BLE Host Task Started" at 444-564 ms after reset and first advertisement at 1854 ms (`ble_multi_conn_prph\README.md` lines 41-42; C6/H2 boards, not S3).

### Inferences
- One-hop notification latency is bounded by the connection interval plus queueing: a 4-byte notification (11-byte LL payload with ATT+L2CAP headers; ~168 us on 1M PHY) is sent at the next connection event of that link, so with interval I the hop costs up to ~I (+ one interval per retransmission). Star topology: touch → hub (≤ I) → hub fans out to N-1 peers over N-1 separate links (≤ I each, in parallel) → ≤ 2I plus processing. With I = 15-30 ms the 100-200 ms target has headroom; with NimBLE's default 30-50 ms it is still met in the no-interference case.
- Applying Espressif's own formula to small packets instead of 251-byte PDUs: a 27-byte LL payload is ~296 us, so ((296 x 2) + 150) x 9 links ≈ 6.7 ms, i.e. the radio could in principle service 9 small-packet links inside 7.5 ms; the practical floor on the S3 is set by the closed controller's scheduler and Wi-Fi slicing, not by air time. A conservative choice that follows both the "5 ms per link" rule and the Wi-Fi slicing: 15 ms for 2 links (3 devices), 45-50 ms for 9 links (10 devices).
- Under a 50/50 Wi-Fi/BLE slicing with periods > 100 ms, a connection event scheduled inside the Wi-Fi slice can be lost, so worst-case latency grows to "interval + the remaining Wi-Fi slice" (tens of ms) and short supervision timeouts (< several hundred ms) become risky; the forum reports of drops at 1.3 s timeouts under heavy MQTT suggest keeping timeouts in the 2-4 s range (NimBLE's default 2.56 s is already there) and limiting Wi-Fi traffic bursts (OTA will be the worst case).
- Reconnection after a drop costs supervision timeout (dead-peer detection, 2.56 s default) + rediscovery (adv interval + scan window: ~0.1-1 s in the logs) + service discovery (the S3 example log shows ~1.7 s for a full `peer_disc_all`, lines 77-103; caching handles avoids this). After a power cycle add ~0.5-2 s boot-to-advertising. Expect 1-5 s total unless handles are cached and the supervision timeout is short.

### Gaps
- No measured end-to-end notification latency (touch → remote display) on ESP32-S3 with Wi-Fi active was found anywhere; the 100-200 ms target can only be argued from interval arithmetic.
- No Espressif figure for the minimum safe connection interval on the S3 with 2-9 links under Wi-Fi coexistence; the "5 ms per link" rule is from the C6/H2 vendor-API example.
- The two esp32.com threads could not be read in full (bot check); IDF versions, exact dates and Espressif staff replies in them are unverified.
- Core-spec link-layer acknowledgement/retransmission semantics were not fetched from a primary source (see KQ4).

## KQ3. Topology for N symmetric devices with no fixed server: hub vs full mesh of connections vs chain, peer discovery, role election, hub loss, and any existing symmetric multi-role example

### Takeaway
The S3 supports all the building blocks (advertise a service UUID, scan, connect as central, accept as peripheral, keep up to 9 links) but Espressif ships no symmetric "mesh of connections" example and none was found in the community; the only official multi-role examples are `ble_gattc_gatts_coex` (S3, one link per role, restarts advertising only after a disconnect) and `ble_multi_conn` (C6/H2 vendor API). A full mesh of N(N-1)/2 links fits the S3 limits up to N = 10 (9 links each, no spare activity for scanning), a star hub holds N-1 links and must be re-elected if it leaves, and a chain adds one connection interval per hop.

### Cited Findings
- Discovery by advertised UUID: the S3 example only connects if the advertisement is connectable (`ADV_IND` or `DIR_IND`) and lists the 16-bit service UUID 0x1811 in its adv data — `COEX_MAIN` lines 89-118, 500-504; the C6/H2 central filters on the advertised complete name `"esp-multi-conn"` instead — `MULTI_CENT` lines 17, 86-95. Passive scan with controller duplicate filtering: `disc_params.filter_duplicates = 1; passive = 1` — `COEX_MAIN` lines 438-444; scan duration 120 s then stop — line 453.
- Both roles active at once from the sync callback (advertise + scan) — `COEX_MAIN` lines 538-541, `MULTI_CENT` lines 420-427 — and after disconnect the S3 example "only restarts advertising" (scan restart is left as `#if 0` TODO) — `COEX_MAIN` lines 326-336.
- Address trick in the official example: to let one board connect several times to one peer it generates a new static random address before each connection (`ble_hs_id_gen_rnd` / `ble_hs_id_set_rnd`) — `MULTI_CENT` lines 330-336, `MULTI_PRPH` lines 83-90; the tutorial notes "the peer may reject duplicate connections. Therefore, before initiating a connection, it is necessary to change your own static random address." — walkthrough line 252.
- Peripheral-initiated parameter update exists (the get-started example has the peripheral request latency 3 after connecting) — `ble-connection.rst` lines 252-256, 361.
- Peer-selection tie-break pattern used by Espressif in the ESP-NOW example: both devices broadcast, "compares the local magic number with that in the data. - Searches for a symmetric multi-role connection mesh on ESP32 ("multi-role", "every node central and peripheral", "lowest address", "connection mesh multi-hop relay NimBLE") returned only ESP-BLE-MESH documentation (flooding mesh over advertising, relay up to 126 hops, GATT proxy) and 2016-2017 Bluedroid forum threads about running GATT client and server at once — [ESP-BLE-MESH Terminology](https://docs.espressif.com/projects/esp-idf/en/v5.1.3/esp32/api-guides/esp-ble-mesh/ble-mesh-terminology.html), [esp32.com "BLE GATT_Server and GATT_Client at the same time possible?" (2016-17)](https://esp32.com/viewtopic.php?p=5983). The NimBLE-Arduino docs state the stack "supports Broadcaster, Observer, Peripheral, and Central roles concurrently" on ESP32/C3/S3/C6 — [NimBLE-Arduino docs mirror](https://docsearch.algolia.com/mcp/docs/repo/h2zero/nimble-arduino) (secondary).

### Inferences
- Link counts: star = N-1 links on the hub, 1 on each leaf (hub needs `MAX_CONNECTIONS = N-1 ≤ 9`, leaves keep the default 3); full mesh = N(N-1)/2 links, N-1 per device (3 devices → 3 links, 2 each; 5 → 10 links, 4 each; 10 → 45 links, 9 each, which is exactly the S3 host maximum and leaves one controller activity for advertising only, so late joiners must be found by the newcomer's own scan while incumbents advertise); chain = N-1 links, 2 per interior device.
- Deterministic role election without a server: every device advertises the demo's 128-bit service UUID and scans; on seeing a peer whose address is numerically higher (or lower; any strict order works) it initiates, otherwise it waits to be connected. Because NimBLE allows only one outgoing connect at a time and (by default) pauses scanning for it, a device joining a 9-peer mesh will form its links sequentially (each ~0.1-1 s per the logs), and must restart scanning after each connect/disconnect (the S3 example leaves this out). The whitelist (`BT_NIMBLE_WHITELIST_SIZE` up to 15) can restrict connects to known addresses once the group is learned.
- Full mesh gives one-hop latency (≤ 1 interval) and no single point of failure but each device runs 2-9 connection schedules under the closed controller plus Wi-Fi slicing; the Multi-Connection Guide's "raise the interval with link count" applies per device, and on each link the central side sets the parameters, so in a mesh the per-link intervals are chosen by whichever device won the election for that link (make the rule symmetric: both sides request the same interval).
- Hub leaving (star): every leaf gets `BLE_GAP_EVENT_DISCONNECT` after the supervision timeout (2.56 s default), resumes advertising + scanning, and the election rule picks a new hub (e.g. lowest address among those still visible); until then leaves have no path to each other. A full mesh degrades gracefully (only the leaver's N-1 links drop). A chain breaks into two halves if an interior node leaves and relay adds ~1 interval per hop (latency ≈ hops x interval, so a 10-node chain at 30 ms is ~270 ms worst case, over the target).
- Because the demo state is tiny (RGB + holding flag), a simpler symmetric scheme is "every device is a GATT server with one notify characteristic; every device is also a client subscribed to every peer" over the mesh links, so a touch is one `ble_gatts_notify_custom()` per link (N-1 calls) with no relaying.

### Gaps
- No Espressif or community reference implementation of address-based role election or a symmetric multi-role connection mesh on ESP32 was found; the design above is unverified in practice on the S3.
- Whether the S3 controller tolerates 9 links each in a different role mix with Wi-Fi connected is not documented; the Multi-Connection Guide's 9 is a maximum, not a tested-with-Wi-Fi figure.
- How quickly NimBLE on the S3 can form many links back-to-back (connect procedures are serialised) was only inferred from C6/H2 logs.

## KQ4. Reliability: acknowledged connection link layer versus unacknowledged advertising, and what retransmission buys under interference

### Takeaway
Only partially sourced: Espressif's docs confirm that a connection exchanges a packet pair every interval regardless of data and that a link is declared dead after the supervision timeout, while ESP-NOW's docs confirm that even its MAC-layer status does not guarantee application delivery and recommend application ACK + retransmit + sequence numbers. The link-layer ACK/retransmit mechanism itself (no loss, only added delay in multiples of the interval) is standard Bluetooth Core behaviour that was not fetched from a primary source here.

### Cited Findings
- Connection events exchange a central→peripheral and peripheral→central packet each interval, with empty packets when there is nothing to send, and data that does not fit waits for the next interval — `ble-connection.rst` lines 43, 54. A link is dropped only after the supervision timeout (100 ms to 32 s range) with no successful event — line 68; `HCI_COMMON_H` lines 1813-1815.
- ESP-NOW (for contrast): "It will return ESP_NOW_SEND_SUCCESS in sending callback function if the data is received successfully on the MAC layer. Otherwise, it will return ESP_NOW_SEND_FAIL. ... It is not guaranteed that application layer can receive the data. If necessary, send back ack data when receiving ESP-NOW data. If receiving ack data timeouts, retransmit the ESP-NOW data. A sequence number can also be assigned to ESP-NOW data to drop the duplicate data." — `ESPNOW_RST` line 118. "Encrypting multicast vendor-specific action frame is not supported." — line 79.
- Advertising on the S3 controller under coexistence is subject to flow control: "advertising reports will be discarded by the controller if the number of unprocessed advertising reports exceeds the size of BLE adv report flow control" (`BT_CTRL_BLE_ADV_REPORT_FLOW_CTRL_NUM`, range 50-1000, default 100) — `CTRL_KCONFIG` lines 232-253; and only "one event in every N" advertising events gets high priority against Wi-Fi — `COEXIST_RST` line 214.
- GATT offers acknowledged (indication, `ble_gatts_indicate`) and unacknowledged-at-ATT (notification, `ble_gatts_notify` / `ble_gatts_notify_custom` / `ble_gatts_notify_multiple_custom`) delivery — `C:\Espressif\esp-idf\components\bt\host\nimble\nimble\nimble\host\include\host\ble_gatt.h` lines 888-948, 1007-1019.

### Inferences
- In a connection, a notification is carried in an LL data PDU that the peer acknowledges in the same connection event; a corrupted PDU is retransmitted at the next event, so the application sees no loss but a latency step of +1 interval per retry, and prolonged interference surfaces as a supervision-timeout disconnect rather than silent drops. (Bluetooth Core Spec Vol 6 Part B link-layer acknowledgement; stated from general knowledge, not from a fetched source.) ATT notifications ride on this reliable link, so "unacknowledged" at the ATT layer still means delivered-or-disconnected.
- Advertising-based sharing (and ESP-NOW broadcast) has no per-frame acknowledgement; reliability comes only from repetition, and the S3 drops advertising reports under backlog and loses low-priority advertising events to the Wi-Fi slice, so a single touch event sent once by advertisement can be missed, whereas on a connection it cannot.
- The flip side: a connection has a hard failure mode (supervision timeout → seconds of outage + reconnection) that advertising does not; for the demo, a short interval with a 2-4 s timeout and reconnection logic covers both.

### Gaps
- No primary-source quote for the LL acknowledgement/retransmission rule or for "broadcast frames are not acknowledged" in 802.11; both are stated from standard knowledge.
- No measured packet-loss or latency-jitter figures for BLE connections on the ESP32-S3 under Wi-Fi traffic were found.

## KQ6. ESP-NOW over Wi-Fi as the comparison point: setup, latency, reliability, same-channel constraint with a router-connected station, modem-sleep warning, v2 payload, max peers, and the fact that it is Wi-Fi

### Takeaway
ESP-NOW is a connectionless Wi-Fi protocol: peers are added by MAC address, broadcast needs no pairing on the receiver, frames are vendor-specific 802.11 action frames at a default 1 Mbps, up to 20 peers (6-7 encrypted), 250 bytes (v1) or 1470 bytes (v2) per frame; community round-trip measurements range from < 1 ms to ~8 ms typical with spikes to 50-200 ms under back-to-back sends. Its hard constraints for this demo are that every device must sit on the same Wi-Fi channel (the station's channel is dictated by its router, and a peer whose channel differs from the home channel cannot be sent to), that broadcast has no acknowledgement, and that a router-connected station in modem sleep may miss ESP-NOW frames. It is not Bluetooth.

### Cited Findings
- Definition and framing: "ESP-NOW is a kind of connectionless Wi-Fi communication protocol that is defined by Espressif. In ESP-NOW, application data is encapsulated in a vendor-specific action frame and then transmitted from one Wi-Fi device to another without connection." Listed among the Wi-Fi driver's features ("The Espressif-specific ESP-NOW protocol and Long Range mode, which supports up to 1 km") — `WIFI_RST` lines 23, 51.

- The esp-now component README gives no latency/throughput numbers, only "supports one-to-many and many-to-many device connection and control" — [github.com/espressif/esp-now](https://github.com/espressif/esp-now).

### Inferences
- For this demo all devices are in one room on one router, so they normally share one channel and ESP-NOW broadcast works with zero pairing (receivers need no peer entry; senders add the broadcast peer with channel 0). The failure cases are: a dual-band/mesh Wi-Fi system whose nodes use different 2.4 GHz channels (or a device that joined on 5 GHz: ESP32-S3 is 2.4 GHz only, so not applicable), a device whose station is disconnected and therefore parked on a channel of its own, and roaming between APs on different channels: in each case that device silently stops hearing the others. The IDF mitigation is to follow the station's current channel (channel 0) and re-read it after every `WIFI_EVENT_STA_CONNECTED`; there is no in-tree mechanism to bridge channels.
- One-hop latency is in the low milliseconds when the medium is idle (a 20-byte frame at 1 Mbps is ~0.5 ms of air time plus driver overhead), i.e. 10-50x lower than a BLE connection interval, but with no ACK on broadcast and bursts of 50-200 ms reported when frames are queued back-to-back; a touch event should be sent as a small broadcast with a sequence number and repeated 2-3 times, or sent unicast to each of ≤ 19 peers (MAC-level ACK and retry) at the cost of N-1 sends per event.
- Because the S3's single radio is time-sliced between Wi-Fi and BLE, ESP-NOW frames compete with the station traffic but not with a second radio technology, and receiving requires the radio to be in the Wi-Fi slice and awake: the modem-sleep warning means `esp_wifi_set_ps(WIFI_PS_NONE)` for reliable reception at the cost of power, and the ESP-NOW wake-window/interval parameters should stay at defaults if BLE is also used.
- ESP-NOW is a Wi-Fi feature (action frames on the 802.11 MAC) and does not involve the Bluetooth controller at all; it therefore does not answer the user's "Bluetooth" requirement and is useful only as the latency/complexity reference point.

### Gaps
- No controlled, published ESP-NOW latency benchmark with numbers in text was found (the Electric UI dataset was not fetched; Espressif's test report PDF in issue #115 is not visible).
- The in-tree conflict between `ESP_NOW_MAX_ENCRYPT_PEER_NUM 6` (header) and "default is 7 ... no more than 17" (docs) was not resolved; it does not matter for an unencrypted broadcast demo.
- No primary source was fetched for "802.11 broadcast frames are not acknowledged"; the IDF docs only say the callback reports MAC-layer reception and that application delivery is not guaranteed.
- The esp32.com WIFI-2245 threads could not be read in full (bot check); the Espressif staff quote is from a search excerpt and dates from 2019-2020.
