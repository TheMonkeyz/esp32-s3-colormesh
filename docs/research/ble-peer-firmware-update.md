# Device-to-device firmware update over BLE between two ESP32-S3 boards (ESP-IDF v5.5.4, NimBLE)

Scope: a board that sees a NEWER version advertised by a peer connects as GATT central, pulls the peer's running
app image (~2 MB) from the peer's running OTA slot, writes it into its own other OTA slot, verifies, reboots with
rollback protection. Both boards keep a low-latency colour-state advertise+scan protocol running.

Sources: the installed ESP-IDF v5.5.4 at `C:\Espressif\esp-idf` (version confirmed by `version.txt` = v5.5.4),
read directly; the esp-iot-solution repository and component registry; GitHub issues. Local file citations give
path + line numbers as read on 2026-10-31. Several esp32.com forum threads could not be read (the site serves a
bot-check page that I did not complete); where I only have the search-engine snippet of such a thread I say so.

## KQ1. Throughput: what to expect, which settings, which direction, resulting time for 2.0–2.5 MB

### Takeaway
Espressif's own NimBLE throughput example (installed, v5.5.4) documents ~500 kbps for Write Without Response and
~340 kbps for Notify at MTU 512 / 7.5 ms interval / DLE 251 on **1M PHY**; Espressif's closing comment on issue
#12789 (Sept 2026) reports ~750–794 kbps (1M) and ~1.33–1.38 Mbps (2M) with the same example. A 2.0 MB image
therefore takes roughly **12–50 s on air** depending on PHY and direction (estimate), plus receiver flash time;
client→server Write Without Response is the faster direction in the documented IDF numbers.

### Inferences
- Air-time estimates for the image alone (no protocol overhead, no flash stalls) — **estimates**, computed from the cited rates:

  | Rate (source) | 2.0 MB (16.8 Mbit) | 2.5 MB (21.0 Mbit) |
  |---|---|---|
  | 340 kbps notify, 1M (README) | ~49 s | ~62 s |
  | 500 kbps write-no-rsp, 1M (README) | ~34 s | ~42 s |
  | 46 KB/s ≈ 370 kbps, S3 stock demo (forum snippet) | ~45 s | ~57 s |
  | 794 kbps, 1M (#12789 closing comment) | ~21 s | ~26 s |
  | 102.5 KB/s ≈ 820 kbps, S3 2M, no logs (forum snippet) | ~20 s | ~26 s |
  | 1.38 Mbps, 2M (#12789 closing comment) | ~12 s | ~15 s |

  Planning figure: budget **~30–60 s** for a 2 MB image on 1M PHY and **~15–30 s** on 2M PHY, then add receiver flash time (KQ3) and any per-sector ACK round trips (each ACK costs at least one connection interval, 7.5 ms; 512 sectors × 7.5 ms ≈ 4 s if the sender waits for every ACK, so use a window of several sectors).
- Direction: in the *documented* IDF numbers client→server Write Without Response (~500 kbps) beats server→client Notify (~340 kbps) by ~45 %; the gap is a host/pipelining artefact, not a radio limit (the notify path needs explicit pipelining of 15 in-flight mbufs and hits `BLE_HS_ENOMEM`). For "the newer board is the server and the older board pulls", the natural GATT direction is Notify (server→client); if the measured gap matters, invert roles for the transfer: let the *newer* board connect as central and push with Write Without Response into the older board's receive characteristic (the version discovery still comes from adverts; whoever is newer initiates).
- Settings checklist that the examples use and that the planning should copy: MTU 512 (`ble_att_set_preferred_mtu(512)` + `ble_gattc_exchange_mtu`; MTU is not exchanged automatically), DLE `set_data_len(251, 2120)`, conn interval 6 units (7.5 ms) with `max_ce_len` 24 (15 ms), `CONFIG_BT_NIMBLE_MSYS_1_BLOCK_COUNT=50`, `TRANSPORT_ACL_FROM_LL_COUNT=20`, 509-byte payloads (MTU−3), NimBLE logging off, host flow control left off on S3 (default), request 2M PHY after connect with `ble_gap_set_prefered_le_phy`. `BT_CTRL_BLE_MAX_ACT` does not raise throughput; it is the activity budget (KQ4).
- `MSYS_1_BLOCK_COUNT=50 × 256 B` plus `MSYS_2 24 × 320 B` is ~20 KB of mbuf pool — cheap on S3.

### Gaps
- No controlled ESP32-S3-specific NimBLE throughput table from Espressif was found; the README figures are chip-agnostic and the #12789 closing figures do not name the chip. The S3 forum numbers (46 and 102.5 KB/s) are snippets of a thread I could not open (bot-check page).
- Whether a 2M PHY update works on a connection established through *legacy* advertising on ESP32-S3 was not verified; the example gates PHY selection behind `CONFIG_EXAMPLE_EXTENDED_ADV`, but the PHY-update procedure is a connection-level LL procedure independent of advertising type. Needs a test.
- Effect of a concurrent 20–100 ms advertising + continuous scanning (the state protocol) on the transfer rate: no measurement found.

## KQ2. Existing building blocks: espressif/ble_ota, other projects, esp_ota_* receive side

### Takeaway
`espressif/ble_ota` (registry 0.1.18, ESP32-S3 supported, NimBLE supported) is a *receiver-only* GATT server with a
simple sector/packet protocol (4096-byte sectors, 16-bit sector index, 8-bit packet sequence, 20-byte ACK with
CRC16) designed for a phone/PC sender; nothing in it prevents an ESP32 NimBLE central from being the sender, but
no ready-made ESP32→ESP32 project exists. The esp_ota_* receive side is `esp_ota_begin` / `esp_ota_write` /
`esp_ota_end` / `esp_ota_set_boot_partition` + the first-chunk `esp_app_desc_t` check at image offset 32.

### Cited Findings — espressif/ble_ota (esp-iot-solution)
- Registry: `espressif/ble_ota` latest 0.1.18, "uploaded 1 month ago" (page read 2026-10-31), supported targets esp32, esp32c3, esp32h2, esp32s3, esp32c2, esp32c6; description "esp ble ota is a firmware upgrade component for data sending and receiving based on customized BLE Services"; the client splits the firmware and sends it in sequence, the receiver checks packet sequence and CRC and returns an ACK; "When using NimBLE, it may be necessary to increase `CONFIG_BT_NIMBLE_HOST_TASK_STACK_SIZE`"; example `examples/bluetooth/ble_ota`; source commit e1a8f5c3e07d17218fbefeec996520536e2d282d — [components.espressif.com/espressif/ble_ota](https://components.espressif.com/components/espressif/ble_ota)
- Source location in esp-iot-solution: `components/bluetooth/ble_profiles/esp/ble_ota/` (include/, src/, proto/, proto-c/, python/, Kconfig, README.md); a newer sibling `ble_ota_raw/` exists — [GitHub tree](https://github.com/espressif/esp-iot-solution/tree/master/components/bluetooth/ble_profiles/esp/ble_ota), [ble_profiles/esp tree](https://github.com/espressif/esp-iot-solution/tree/master/components/bluetooth/ble_profiles/esp)
- Example README (`examples/bluetooth/ble_ota/README.md`): DIS service (software/hardware version) + OTA service with four characteristics: `0x8020` RECV_FW (write, notify: firmware packets and ACKs), `0x8021` PROGRESS_BAR (read, notify), `0x8022` COMMAND (write, notify: commands and ACKs), `0x8023` CUSTOMER (write, notify). Command packets: Command_ID + payload + CRC16; Start OTA 0x0001 (payload = firmware length), Stop OTA 0x0002, Response 0x0003. Firmware packets: sector index, packet sequence, payload; "4 KB per sector", sectors in order, last packet of a sector has sequence 0xFF and its last two payload bytes hold the CRC16 of the whole sector. Reply packets: sector index + ACK status (success, CRC error, sector index error, payload length error). NimBLE config: host "NimBLE - BLE only", preferred MTU 517 "for maximum throughput"; ESP32-S3 pre-encrypted OTA needs NimBLE host task stack 8192; ESP32-H2/C6 must disable "BLE 5 feature" and Extended Adv for the sample app. Sender: Android app `EspressifApps/esp-ble-ota-android`; options for protocomm security, pre-encrypted OTA (`esp_encrypted_img`), delta OTA (`esp_delta_ota_patch_gen.py`) — [example README (raw)](https://raw.githubusercontent.com/espressif/esp-iot-solution/master/examples/bluetooth/ble_ota/README.md)
- Header `include/ble_ota.h`: `esp_ble_ota_recv_fw_cb_t` = `void (*)(uint8_t *buf, uint32_t length)`; `esp_ble_ota_callback_funs_t { recv_fw_cb }`; `esp_ble_ota_host_init(void)`; `esp_ble_ota_recv_fw_data_callback(cb[, esp_decrypt_handle_t])`; `unsigned int esp_ble_ota_get_fw_length(void)`; `esp_ble_ota_finish(void)`; non-Bluedroid branch also `esp_ble_ota_write(uint8_t *file, size_t length)` and `esp_ble_ota_set_sizes(file_size, block_size)`; no UUID or packet-size macros in the header; `CONFIG_PRE_ENC_OTA`, `CONFIG_BT_BLUEDROID_ENABLED` referenced — [ble_ota.h (raw)](https://raw.githubusercontent.com/espressif/esp-iot-solution/master/components/bluetooth/ble_profiles/esp/ble_ota/include/ble_ota.h)
- NimBLE server `src/nimble_ota.c` (as summarised by the fetch; worth re-reading before coding): service `0x8018`; `0x8020` RECV_FW flags `INDICATE|WRITE`, `0x8021` `INDICATE|READ`, `0x8022` COMMAND `INDICATE|WRITE`, `0x8023` `INDICATE|WRITE`; ACKs are sent with `ble_gattc_notify_custom()` (a notification although the characteristics declare INDICATE). Command write: `om_data[0..1]` = `{0x01,0x00}` start / `{0x02,0x00}` stop; start carries the firmware length as 4 little-endian bytes at `om_data[2..5]` (minus `ENC_HEADER` 512 under pre-encryption), mallocs `fw_buf` of `ota_block_size` (default `BUF_LENGTH` 4098) and ACKs status 0x01; no length-vs-partition check. Firmware write: ≥3 bytes; sector index = `om_data[0] + om_data[1]*256`, packet index `om_data[2]`; sector mismatch → ACK status 0x02 with current sector (0xFFFF treated as last sector); packet index 0xFF = end of sector, last 2 bytes (`SECTOR_END_ID`) excluded from the copy; on sector completion data goes straight to `recv_fw_cb` (no ring buffer in this file) and a success ACK (status 0x00) is sent. ACK frame: 20 bytes — bytes 0–1 sector index (command ACKs use 0x03,0x00), byte 2 status, bytes 4–5 current sector on index error, bytes 18–19 CRC16-CCITT (poly 0x1021, init 0) little-endian over bytes 0–17. Incoming firmware CRC is *not* verified in this file (CRC16 only used for ACKs). No `ble_att_set_preferred_mtu` call (BLE_GAP_EVENT_MTU only logged). Advertises name `nimble-ble-ota`, `BLE_GAP_CONN_MODE_UND` + `BLE_GAP_DISC_MODE_GEN`, flags `BLE_HS_ADV_F_DISC_GEN | BLE_HS_ADV_F_BREDR_UNSUP`, includes 16-bit UUID 0x1811; extended-adv variant `nimble-ota-ext`. Calls no `esp_ota_*` function itself — [nimble_ota.c (raw)](https://raw.githubusercontent.com/espressif/esp-iot-solution/master/components/bluetooth/ble_profiles/esp/ble_ota/src/nimble_ota.c)
- Newer `ble_ota_raw` profile (on `esp_ble_conn_mgr`): `esp_ble_ota_raw_init()` registers OTA service 0x8018 + DIS; `esp_ble_ota_raw_set_ota_begin_cb(cb(image_size_bytes))` runs on START "after RAM is allocated and before START CMD ACK" (non-ESP_OK rejects START); `esp_ble_ota_raw_set_sector_send_window_for_ringbuf(capacity)` → window = capacity/4096 clamped 1..64, "sent in START ACK byte 6, byte 7 reserved"; `esp_ble_ota_raw_recv_fw_data_callback(cb)` fires per sector after CRC; `esp_ble_ota_raw_get_fw_length()` returns UINT32_MAX before START; docs say it validates command CRC16, sector/packet continuity and sector CRC16 before delivering data — [esp_ble_ota_raw.h (raw)](https://raw.githubusercontent.com/espressif/esp-iot-solution/master/components/bluetooth/ble_profiles/esp/ble_ota_raw/include/esp_ble_ota_raw.h), [esp-iot-solution docs: BLE OTA](https://docs.espressif.com/projects/esp-iot-solution/en/latest/bluetooth/ble_ota.html)
- Espressif's newer `esp_ota_service` component (registry 0.5.2) has "a native NimBLE GATT server that implements the official ESP BLE OTA app protocol"; its PC test tool "goes through an ESP32-C6 running ESP-AT as the BLE central" (search snippet) — [components.espressif.com esp_ota_service ota_ble example](https://components.espressif.com/components/espressif/esp_ota_service/versions/0.5.2~2/examples/ota_ble)

## KQ3. Sender side: reading the running image, finding its real length, chunking, flash-vs-BLE/display interaction

### Takeaway
Use `esp_ota_get_running_partition()` + `esp_image_get_metadata()` (gives `image_len` *including* the appended
SHA-256) to know exactly how many bytes to send; read them through `esp_partition_mmap()` (cache path, no cache
stall) rather than `esp_partition_read()` (SPI1 path, which disables both caches and non-IRAM interrupts for the
duration); on the receiver, every `esp_ota_write`/erase stalls the other core and non-IRAM ISRs, so keep writes
sector-sized, and keep LCD DMA sources out of flash.

- Sender length determination: `esp_partition_pos_t pos = { running->address, running->size }; esp_image_get_metadata(&pos, &md);` then send exactly `md.image_len` bytes (header → segments → checksum padding → 32-byte SHA-256). Do **not** send `running->size` (the whole slot, typically 0x1F0000–0x200000 bytes of mostly 0xFF): it would double the air time and `esp_ota_end` would still pass but the wasted bytes are pure cost. With secure boot the signature block is beyond `image_len` and must also be sent (`full_image_len` logic, lines 977–1004) — only relevant if secure boot is on.
- Reading: `esp_partition_mmap(running, 0, md.image_len, ESP_PARTITION_MMAP_DATA, …)` maps through the cache (no SPI1 transaction, no cache stall, no IPC to the other core) — the sender then just `memcpy`s 509-byte slices into mbufs. 2 MB of data-space MMU pages must be free; if the mapping fails, fall back to `esp_partition_read` in ≥4 KB pieces and accept the short cache stalls. (estimate: mmap of 2 MB = 32 pages of 64 KB on S3.)
- The sender serves from the slot it is executing from; that is fine for reads (only writes are blocked by `ESP_ERR_OTA_PARTITION_CONFLICT` / dangerous-write checks).
- Receiver flash cost, **estimate** from the 0.647 MB/s raw-write sample: 2 MB ≈ 3.2 s of pure write time during which (per `spi_flash_concurrency.rst` line 47) the other core busy-waits and non-IRAM ISRs are off — split into ~250 × 8 KB chunks of ~13 ms each (or 4 KB chunks of ~6 ms). Erase: no S3 figure found (gap); with `OTA_WITH_SEQUENTIAL_WRITES` the 4 KB erase happens inside each `esp_ota_write` at sector boundaries, spreading the cost; with a known size the whole 2 MB is erased in `esp_ota_begin` (block erases with yields every 20 ms by default).
- BLE during flash writes: the Bluetooth controller on S3 is pinned to a core (`BT_CTRL_PINNED_TO_CORE`, Kconfig lines 29–47) and its link-layer timing must survive cache-off windows; the throughput example and the ble_ota component both write flash from a separate task fed by a queue/ring buffer rather than inside the GATT callback. Plan: GATT callback → ring buffer; OTA task does `esp_ota_write` in 4 KB units; sender's window (3–8 sectors) absorbs the stall. A 15 ms `max_ce_len` means a 13 ms cache-off window can eat one connection event; the LL retransmits, nothing is lost, but throughput dips (inference).
- Display: if any LCD DMA descriptor points at flash-resident data (fonts, images in `.rodata`), copy it to PSRAM/SRAM first, or pause the display refresh during the transfer (docs line 85 is explicit that DMA reads from flash during erase/write return unpredictable data).
- Chunk/ACK scheme (inference from the ble_ota framing and LL semantics): BLE LL already guarantees in-order, loss-free delivery of ATT PDUs within a connection, so sequence numbers mainly serve (a) resume after a disconnect (`esp_ota_resume` at a sector boundary), (b) dropping a packet when the receiver's buffer is full. Use 509-byte payloads = 2 bytes sector index + 1 byte packet seq + 506 data (or 4-byte absolute offset + data), 8 packets ≈ 1 sector, per-sector CRC16 + per-sector ACK, window ≥ 3 sectors so the sender never waits one interval per sector.

### Gaps
- No ESP32-S3 sector-erase / block-erase timing figure from a primary source.
- Whether the S3 BLE controller's interrupt handlers are IRAM-safe (continue during cache-off windows) is not documented in the files read; the forum reports of BLE OTA working at tens of KB/s suggest the LL keeps the link, but it should be measured with the display running.
- The 31× slowdown report on v5.4.2 (secure boot + flash encryption) could not be read in full; its root cause and whether it persists in v5.5.4 are unknown. It only matters if flash encryption is enabled.

### Inferences
- Activity budget: 1 advertising instance + 1 scanner + 1 central connection (+ 1 peripheral connection if the newer board is also being pulled from by a third board) = 3–4 activities ≤ default 6; no need to raise `BT_CTRL_BLE_MAX_ACT`. Set `BT_NIMBLE_MAX_CONNECTIONS` ≥ 2 (default 3 is fine).
- Enable `CONFIG_BT_NIMBLE_HOST_ALLOW_CONNECT_WITH_SCAN=y` so the puller does not have to stop its state-protocol scan to open the OTA connection; alternatively stop the scan for the ~1 s connection setup and resume (the coex example does this implicitly with a 120 s scan).
- Scan duty during a 7.5 ms-interval connection: a connection event with `max_ce_len` 15 ms can occupy the whole 7.5 ms interval, so the scanner gets whatever radio time is left; expect the state protocol's packet-reception rate to drop markedly during the transfer (no number available; treat as "degrades gracefully": state updates still arrive but with higher latency/loss). Mitigations: raise the OTA connection interval to 15–30 ms when the transfer is not time-critical, or shrink `max_ce_len`; the adv-report flow control (100 queued reports) will also drop reports if the host task is busy feeding flash.
- Duplicate filtering must be "by device address and advertising data" (or off) for a state protocol whose payload changes from the same address, otherwise the controller suppresses the updates.

### Gaps

### Inferences
- Simplest design (legacy API only, no EXT_ADV): make the single state advertisement ADV_IND (`conn_mode = BLE_GAP_CONN_MODE_UND`) at the state-protocol rate (≥ 20 ms is legal for connectable), include the Flags AD (3 bytes: `BLE_HS_ADV_F_DISC_GEN | BLE_HS_ADV_F_BREDR_UNSUP` as in nimble_ota.c), put the version in the manufacturer-specific AD (project id + X.Y.Z + rc + "pending verify" bit) and keep ≤ 31 bytes. Costs: every peer scanner may send SCAN_REQ (ADV_IND is also scannable) — set an empty scan-response and, if scan requests bother the radio budget, an `adv_filter_policy` that only answers whitelisted peers; when a peer connects, the legacy instance stops and must be restarted from `BLE_GAP_EVENT_CONNECT` (and the second connection slot must exist, `MAX_CONNECTIONS ≥ 2`, or the board is not pullable while itself pulling).
- Two-instance design (EXT_ADV on, `MAX_EXT_ADV_INSTANCES` = 2): instance 0 = legacy-PDU non-connectable state beacon at the fast rate (legacy-PDU so that scanners without extended scanning still see it), instance 1 = legacy-PDU connectable "OTA available v X.Y.Z" at 100 ms–1 s. Each instance gets its own (random) address unless configured otherwise, so the state protocol's "who is who" must key on the payload, not the address. Whether the Espressif S3 controller accepts a legacy non-connectable instance below 100 ms is not verified (gap) — the ADV_NONCONN 100 ms floor is a BLE 4.x rule and the S3 controller is BLE 5.0.
- Connectable advertising does not change the state-broadcast payload rules except the mandatory Flags AD (3 bytes) and the fact that unknown centrals may connect: add a check in the OTA GATT server that only serves peers with the same `project_name` and that any other connection is dropped quickly (`ble_gap_terminate`).

### Gaps
- Not verified on hardware: whether the ESP32-S3 controller enforces the 100 ms floor for legacy non-connectable PDUs (via either API), and whether the legacy `ble_gap_adv_start` API remains usable when `BT_NIMBLE_EXT_ADV=y` (the examples switch to the ext API entirely, which suggests not).

## KQ6. Safety: verification, rollback, power loss, serving from an unconfirmed image, name/version rules

### Takeaway
`esp_ota_end` + `esp_ota_set_boot_partition` already verify magic, segments, checksum, appended SHA-256 (and secure
boot signature); `CONFIG_BOOTLOADER_APP_ROLLBACK_ENABLE` gives the new image exactly one boot to call
`esp_ota_mark_app_valid_cancel_rollback()`; power loss mid-transfer is harmless because the running slot and the
two-sector otadata are untouched until the end; a board still in `ESP_OTA_IMG_PENDING_VERIFY` cannot even start a
download (`esp_ota_begin` refuses) and should also refuse to *serve*.

### Cited Findings
- `CONFIG_BOOTLOADER_APP_ROLLBACK_ENABLE` (default n): "After updating the app, the bootloader runs a new app with the "ESP_OTA_IMG_PENDING_VERIFY" state set. This state prevents the re-run of this app ... If the app is working, then it is marked as valid. Otherwise ... rolls back to the previous working app ... Note: If during the first boot a new app the power goes out or the WDT works, then roll back will happen. Rollback is possible only between the apps with the same security versions." — [bootloader/Kconfig.app_rollback lines 3–13](file:///C:/Espressif/esp-idf/components/bootloader/Kconfig.app_rollback)
- Rollback process (ota.rst): `esp_ota_set_boot_partition` sets `ESP_OTA_IMG_NEW`; the bootloader turns NEW into `PENDING_VERIFY` and a still-pending image into `ABORTED` on the next reset; "a new application has only one attempt to boot successfully"; "Recommendation: Perform the self-test procedure as quickly as possible, to prevent rollback due to power loss"; "Only OTA partitions can be rolled back. Factory partition is not rolled back." — [ota.rst lines 41–49, 85–120](file:///C:/Espressif/esp-idf/docs/en/api-reference/system/ota.rst)
- `esp_ota_begin` refuses while the running app is pending: "Running app has not confirmed state (ESP_OTA_IMG_PENDING_VERIFY)" → `ESP_ERR_OTA_ROLLBACK_INVALID_STATE` — [esp_ota_ops.c lines 165–170](file:///C:/Espressif/esp-idf/components/app_update/esp_ota_ops.c); "Confirm the running app before to run download a new app" — [esp_ota_ops.h lines 81–83](file:///C:/Espressif/esp-idf/components/app_update/include/esp_ota_ops.h)
- Safe update mode: "even if the power is cut off during the update, the chip will remain operational and capable of booting the current application ... Once the image is verified, the OTA Data partition is updated"; otadata "is two flash sectors (0x2000 bytes) in size, to prevent problems if there is a power failure while it is being written" — [ota.rst lines 13–15, 34](file:///C:/Espressif/esp-idf/docs/en/api-reference/system/ota.rst)
- Verification content of `esp_image_verify`: magic, partition < 16 MB, segments fit, 8-bit checksum, "SHA-256 of image is valid (if image has this appended)", signature if enabled — [esp_image_format.h lines 100–106](file:///C:/Espressif/esp-idf/components/bootloader_support/include/esp_image_format.h); `esp_ota_end` calls it (esp_ota_ops.c 457–461) and `esp_ota_set_boot_partition` calls `image_validate` again (605–607).
- Anti-rollback (`CONFIG_BOOTLOADER_APP_ANTI_ROLLBACK`, eFuse `secure_version`, 16-bit on non-ESP32 chips = 16 increments) is a separate, optional mechanism; "The next update of app is possible if a running app is in the ESP_OTA_IMG_VALID state" — [ota.rst lines 147–210](file:///C:/Espressif/esp-idf/docs/en/api-reference/system/ota.rst)
- Version check in the IDF example is equality-only `memcmp` on the 32-byte `version` string, and it also refuses an image whose version equals `esp_ota_get_last_invalid_partition()`'s — [native_ota_example.c lines 169–185](file:///C:/Espressif/esp-idf/examples/system/ota/native_ota_example/main/native_ota_example.c)
- `esp_ota_get_state_partition()` returns `ESP_ERR_NOT_FOUND` when "state was not found for given partition" (i.e. factory/undefined) — [esp_ota_ops.h lines 393–404](file:///C:/Espressif/esp-idf/components/app_update/include/esp_ota_ops.h)

### Inferences
- Acceptance rule for the receiver, applied on the first 288+ bytes: `desc.magic_word == 0xABCD5432`, `strncmp(desc.project_name, running.project_name, 32) == 0`, `semver(desc.version) > semver(running.version)`, `desc.version != last_invalid.version`, and (if anti-rollback) `esp_efuse_check_secure_version(desc.secure_version)`. Also compare `desc.idf_ver`/`mmu_page_size` only if the project ever changes those.
- Sender rule: advertise/serve only when `esp_ota_get_state_partition(running) == ESP_OTA_IMG_VALID` (or `ESP_ERR_NOT_FOUND`/`UNDEFINED` for a factory image). While `PENDING_VERIFY`, the image has not proven itself; if it later rolls back, the peer that copied it keeps a version the fleet has effectively rejected, so refusing to serve (and clearing the "update available" bit in the advert) is the safe choice. Call `esp_ota_mark_app_valid_cancel_rollback()` only after the app's real self-test (display up, BLE host synced, state protocol running) — then also check `esp_ota_check_rollback_is_possible()`.
- Power loss mid-transfer: nothing to do — the receiver boots its old slot; optionally persist the sector count in NVS and use `esp_ota_resume(partition, OTA_WITH_SEQUENTIAL_WRITES, offset, …)` to continue, provided the sender's image (SHA-256 from its `esp_image_metadata_t.image_digest`) is unchanged; otherwise restart from zero.
- End-to-end integrity: send the sender's `image_digest` (32 bytes) in the START command; `esp_ota_end` will independently verify the appended SHA-256, so a mismatch is caught even without per-chunk CRCs; keep a per-sector CRC16 only to fail fast.
- Version string format: `CONFIG_APP_PROJECT_VER` / `version.txt` / git describe (whatever the project uses) must be parseable: `X.Y.Z` with optional `-rcN`; order rc < release; a parse failure should block the update rather than guess.

### Gaps
- No IDF helper for semantic version comparison was found in the installed tree; this is a local implementation.

## KQ7. Known issues (esp-idf / esp-iot-solution) relevant to NimBLE OTA on ESP32-S3

### Takeaway
The one issue that directly touches v5.5.x — host-flow-control stalls/connection loss on ESP32/C3/S3 in v5.5.3
(IDFGH-17350) — is fixed in v5.5.4 (and flow control is off by default on S3 anyway). The recurring practical
problems are: ATT MTU not exchanged automatically, DLE formerly not raised, mbuf exhaustion (`BLE_HS_ENOMEM`) in
notify pipelines, flash writes starving tasks, and dramatic `esp_ota_write` slowdowns with secure boot + flash
encryption.

### Cited Findings
- esp-idf #18323 (IDFGH-17350), "Potential NimBLE Host Connection Loss in ESP-IDF v5.5.3 release on ESP32 / ESP32C3 / ESP32S3", opened 2026-03-09 by Espressif, closed 2026-03-30: "issue in the host flow control handling may cause BLE data transmission to stall or behave incorrectly" possibly leading to connection loss; "Flow control is enabled by default on ESP32 and disabled by default on ESP32-C3 and ESP32-S3"; workaround disable `CONFIG_BT_NIMBLE_HS_FLOW_CTRL`; "The fix for this issue has been included in IDF v5.5.4 release." — [GitHub #18323](https://github.com/espressif/esp-idf/issues/18323)
- esp-idf #12789 (IDFGH-11677), NimBLE vs Bluedroid GATT performance, opened 2023-12-13, closed 2026-09-21: DLE not raised with ATT MTU before the fix (27-byte LL fragments), `ble_gap_write_sugg_def_data_len()` only before connection, bonded-iPhone LL_LENGTH_REQ rejection worked around with `ble_gap_set_data_len()`; closing comment: NimBLE sets 251-octet LL size on connection; ATT MTU still not exchanged automatically; default preferred MTU 256 — [GitHub #12789](https://github.com/espressif/esp-idf/issues/12789)

- Forum (snippets only): `esp_ota_write` 31× slower (8 KB: 90 ms → 2,850 ms) after moving to v5.4.2 with secure boot v2 + flash encryption in a BLE OTA receiver — [esp32.com p=149359](https://esp32.com/viewtopic.php?p=149359); 8 kB 25 ms → ~400 ms with flash encryption + secure boot v2 (2023) — [esp32.com p=123197](https://esp32.com/viewtopic.php?p=123197); "on an ESP32-S3, whenever esp_ota_begin() is called, the device resets itself within a second or two" (no cause given) — [esp32.com p=147796](https://esp32.com/viewtopic.php?p=147796); ESP32-S3 `esp_ota_end()` failure thread — [esp32.com p=125628](https://esp32.com/viewtopic.php?p=125628); ble_ota example standalone build failure on v5.3.4/S3 — [esp32.com p=152905](https://esp32.com/viewtopic.php?p=152905)
- Older BLE OTA slowness was often the *client's* small MTU (iOS app) rather than the ESP32 — [esp32.com p=110578](https://esp32.com/viewtopic.php?p=110578)
- Controller adv-report flow control drops reports beyond 100 unprocessed — [esp32c3/Kconfig.in lines 232–253](file:///C:/Espressif/esp-idf/components/bt/controller/esp32c3/Kconfig.in)

### Inferences
- On v5.5.4 with S3 defaults (host flow control off), the IDFGH-17350 stall is not a concern; do not turn `BT_NIMBLE_HS_FLOW_CTRL` on.
- Explicitly do the MTU exchange and DLE request on connect (as the throughput example does) and verify via `BLE_GAP_EVENT_MTU` / `BLE_GAP_EVENT_DATA_LEN_CHG` before starting the transfer; log `ble_att_mtu(conn)`.
- Size `MSYS_1_BLOCK_COUNT` to 50 and treat `BLE_HS_ENOMEM` as "back off one tick and retry", never as data loss.
- Avoid flash encryption/secure boot on the OTA slots unless the write-speed regression is retested on v5.5.4.

- Issue #13637, cited in a forum reply as a companion to #12789, was not retrieved.

## Summary of numbers for planning (all estimates derived from cited figures)

- Air transfer of a 2.0 MB image: 1M PHY write-no-rsp ~34 s (README 500 kbps) to ~21 s (#12789 794 kbps); notify 1M ~49 s (340 kbps); 2M PHY ~12–26 s (1.38 Mbps … 102.5 KB/s). 2.5 MB: scale by 1.25.
- Receiver flash write ~3–4 s total at the sampled 0.647 MB/s raw write rate, interleaved; erase time unknown on S3 (sequential erase hides it inside writes).
- Per-sector ACK round trip ≥ 7.5 ms → use a window of ≥ 3–8 sectors; 2 MB = 512 sectors of 4 KB = ~4,150 packets of 506 bytes.
- Overall target: **well under 1 minute** on 1M PHY, ~20–30 s on 2M PHY, with the state protocol degraded (scan reports delayed/dropped) for that period.
